/create-tasks

← Back to index

Summary

A team plan turned into checkbox tasks that name real files and can be picked up one by one. Reads an existing <feature-name>-team-plan.md from /plan-maker-for-team and writes a task breakdown: a Mermaid dependency graph, vertical-slice phases (walking skeleton first), single-role tasks with their own tests, and a mandatory close-out task.

Before writing anything it investigates the codebase with three read-only subagents, re-run fresh even if the plan's author already investigated, so it also works standalone in a later session. The result is one file, <feature-name>-tasks.md, in the same folder as the plan.

When to use

The team agreed the contracts and scenarios in a team plan, but nobody can start work from it: the plan deliberately holds no tasks. /create-tasks is the downstream step that produces the ordered, checkable list each role works from.

Trigger phrases (from the SKILL.md):

  • "break it into tasks"
  • "generate the task breakdown"
  • "create tasks for the plan"
  • /create-tasks

It requires an existing team plan as input. If none exists yet, it tells you to run plan-maker-for-team first and stops — it never invents a plan.

Invocation

/create-tasks <feature-name>-team-plan.md
/create-tasks <feature-name>-brief.md
/create-tasks <feature-name>

Give the plan path directly, or a brief path or feature name — then it looks for the sibling <feature-name>-team-plan.md in the same folder.

What it does, in order:

  • Reads the plan and picks the slicing tooling. It slices the phases with the vertical-slicer skill when it is installed, else with a built-in simplified method, and tells you which one it uses.
  • Investigates with three parallel read-only subagents — backend-grounding, frontend-grounding, tester-grounding — that find the real files, patterns, dependency order and test setup. Without a subagent tool it runs the same three investigations itself, inline.
  • Writes the tasks and phases, runs a self-check, and writes <feature-name>-tasks.md.
  • Back-links the plan: adds a **Tasks:** bullet to the plan's ## References section (skipped if it already points to this file).
  • Audits links: rewrites bare target-project file paths in the prose as Markdown links and warns about any link that does not resolve on disk.
  • Estimates: runs /estimate <tasks path> --from <plan path> and writes **Story Points:** <SP> — estimated <YYYY-MM-DD> with /estimate right after the title. A failed estimate is reported and leaves the file without the line.

Rules the output always satisfies:

  • Phases are vertical slices, each a working end-to-end increment. The first is the walking skeleton carrying the data/model foundation; there is no separate "integrate" phase. A short Kickoff comes first, the Close-out last.
  • Test ownership: unit and integration tests belong to the implementing dev, written test-first; the tester owns e2e and manual tests only. Every #manual_test has a companion #e2e_test, unless the tester-grounding agent confirms it is non-automatable — then it carries (non-automatable: <reason>).
  • No code, real names: components, types and files come from the investigation, not from guessing. Unknowns the plan does not answer go to an **Open questions** section, numbering continuing from the plan's Q#.
  • Stable IDs: K#/BE-#/FE-#/T-#, never renumbered on later edits. completes cites the plan's S#/C# verbatim.
  • Tags: the role tag ends each task title (#frontend-role, #backend-role, #tester-role, #team); the test-type tag starts each test line (#unit_test, #integration_test, #e2e_test, #manual_test).
  • Decimal-hour estimates (1.0h, 2.0h, 4.0h) — never days or T-shirt sizes.
  • Mandatory close-out task (#tester-role): update all documentation per the plan, fix all warnings, run the full test suite and fix every failing test, and fact-check each acceptance criterion one by one.
  • Nothing floats: every task, tester tasks included, sits in the slice whose scenario it verifies; the graph has one subgraph per phase.

Task size: one role, checkable by a reviewer in one sitting, about 2–4 tests. Split a task that spans layers, covers unrelated behaviours or exceeds roughly 1–2 days; never make a task for a single trivial test.

- **Plan:** [multi_sound_playback-team-plan.md](./multi_sound_playback-team-plan.md) — the full team plan (contracts, scenarios, architecture, allocation). **Always read the plan before you start planning the next task** — ...

```mermaid
    BE4["BE-4 player pool"]
    FE2["FE-2 handoff"]
    T1["T-1 e2e"]
    ...
  end
  ...
  T4([T-4 · close-out & acceptance])

  K1 --> BE1 & FE1
  BE4 --> T1
  FE2 --> T1
  ...
```

- [ ] **K1** — Agree the Contracts and Scenarios with the team #team
    - — · 1.0h
    - completes C1, C2
    - Tests

### Phase 1 · Core multi-play *(the walking skeleton: multiple sounds play and persist, end-to-end)*
...

        ...

    - — · 6.0h

Example 2 — No team plan yet (illustrative example)

Input:

/create-tasks Documentation/Backlog/csv-import-brief.md

Output / Result:

No csv-import-team-plan.md next to the brief in Documentation/Backlog/.
A task breakdown needs an existing team plan — run /plan-maker-for-team Documentation/Backlog/csv-import-brief.md first, then /create-tasks again.

It stops there: no tasks file is written and no plan is invented.

Related tools

  • /plan-maker-for-team — Writes the <feature-name>-team-plan.md this skill requires; its S#/C# IDs are what every task's completes cites.
  • /vertical-slicer — When installed, sets the phase boundaries, their order and the walking skeleton; without it the built-in simplified slicing is used.
  • /implement — Executes the tasks file, next task or all, following its **Plan:** link for context.
  • /estimate — Called at the end to write the **Story Points:** line, updating the team plan's entry in .estimation.json instead of adding a second one.
