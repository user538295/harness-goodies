/double-check

← Back to index

Summary

Every reviewer you trust, one target, one merged list of findings. Runs each item in your project's .double-check.json — skills and commands, agents, MCP servers, CLI tools, Markdown rule files — on the same target, then collapses the results into one line per finding, sorted by severity.

Read-only. It never edits, stages, or commits the files it reviews; the only project file it writes is .double-check.json.

When to use

You run /da-review, then /clean-code-review, then the linter, then remember the rules in AGENTS.md — and each one speaks its own format. /double-check runs them all in parallel, checks first that each one is actually installed and ready, and hands you a single list instead of five reports.

The skill declares no trigger phrases beyond the command. Invoke it with /double-check, or ask to double-check changes or files with all configured reviewers, or ask which configured reviewers are available.

Invocation

/double-check [TARGET] [per-item parameters]
/double-check init
/double-check status

Targets (default: all local changes):

  • none or local — staged, unstaged, and untracked changes. Without git there is nothing to diff, so the skill asks what to check.
  • One ref — abc123, HEAD — the files that commit touched.
  • A range — A..B or A...B. Commit and range targets need git; without it the run stops with Nothing to check: not a git repository.
  • Files, folders, or globs — *.h tests/. Works without git.
  • A described file set — all files except tests/. Ambiguous prose makes the skill ask which files you mean before it continues.

Per-item parameters go in the same sentence as the target: /double-check check src/ and run shellcheck with -S warning. They combine with each entry's args in the config; for one run the invocation wins where the two conflict, and the file stays unchanged.

.double-check.json sits at the project root (the git top level, or the current directory without git). It is a JSON array; each entry has exactly one type key plus an optional args string:

  • { "skill": "/brooks-review" } — a skill, command, or plugin
  • { "agent": "security-reviewer" } — an agent type
  • { "mcp": "playwright" } — a connected MCP server
  • { "tool": "eslint", "args": "--max-warnings 0" } — a CLI tool
  • { "md": "conventions.md" } — a Markdown file of rules and guidelines

When the file is missing, the skill creates it with the default config — /da-review, /clean-code-review, /brooks-review, /open-code-review, markdownlint, shellcheck, and AGENTS.md as a strict rule file — and tells you in one line. A broken entry (not an object, zero or several type keys, a non-string args) or an unknown key is listed one per line with a suggested fix, and the run continues with the corrected config.

init creates the default config and prints its path — or just prints the path when the file already exists, leaving it untouched. status prints every configured item with its args and whether it is available — ✅ 🛠 eslint (args: --max-warnings 0) — and reviews nothing.

Availability gate. Before any reviewer starts, the skill prints a Check availability: block: ✅ or ❌ per item, dependencies of a skill listed on their own line above it. Reasons: not found · not installed · not connected · not ready: … · installed, but there is no … in the target · not applicable: … · missing dependency …. A fix that needs no secret and no choice from you — installing a documented CLI — runs by itself. Anything interactive (credentials, a login) stops the run until you answer retry, continue (review without them), or stop. The skill never asks for a secret in chat.

How items run. Every item runs in a subagent, in parallel; heavy or slow items get their own, quick deterministic tools share one. Tool-native severities are mapped onto the rubric (shellcheck error → Major, warning → Moderate, info/style → Minor). With no subagent tool in the harness, the items run inline and the summary says Review ran inline, not independent.

Finding line — one per finding, at most 255 characters:

emoji [item] · Severity · Short name/category | path/to/file.ext:N | Explanation and a short fix.

The same root cause at the same location from several items merges into one line, items comma-joined. Sorted by severity, then path, then line. Items that crashed or were skipped at the gate end up in a final Not run: block.

Severity levels: Critical (blocks correctness, security, or safety) · Major (significant design flaw, missing requirement, or likely bug) · Moderate (suboptimal but workable) · Minor (style, naming, or nitpick)

Example 1 — Local changes, default config (illustrative example)

Input:

/double-check

Output / Result:

Target: local — 4 files

Check availability:
   ✅ 🧠 /devils-advocate
   ✅ 💡 /da-review
   ✅ 💡 /clean-code-review
   ✅ 💡 /brooks-review
   ✅ 💡 /open-code-review
   ✅ 🛠 markdownlint
   ❌ 🛠 shellcheck: installed, but there is no shell script in the target
   ✅ #️⃣ AGENTS.md

💡 [da-review] · Major · Unchecked payment result | src/services/PaymentProcessor.ts:34 | charge() result is ignored; an order can be marked paid without payment. Check the result before updating status.
💡💡 [clean-code-review, brooks-review] · Major · Single Responsibility | src/services/UserService.ts:12 | Split UserService: move auth, email, and billing into separate classes.
#️⃣ [AGENTS.md] · Moderate · Avoid magic numbers | src/services/PaymentProcessor.ts:58 | Replace the literal 3 with a named RETRY_LIMIT constant.
🛠 [markdownlint] · Minor · MD022 | README.md:14 | Surround the heading with blank lines.

Example 2 — Commit range with a blocked reviewer (illustrative example)

Input:

/double-check HEAD~2..HEAD

Output / Result:

Target: range HEAD~2..HEAD — 6 files

Check availability:
   ✅ 🧠 /devils-advocate
   ✅ 💡 /da-review
   ✅ 💡 /clean-code-review
   ❌ 💡 /open-code-review: not ready: no LLM provider configured (ocr llm test failed)
   ✅ 🛠 markdownlint

Blocked — run the fixes, then answer `retry`, `continue` (review without them), or `stop`:
   ❌ 💡 /open-code-review: not ready: no LLM provider configured (ocr llm test failed) → run: ocr config provider

Input:

continue

Output / Result:

💡 [clean-code-review] · Critical · [safety-01] Resource Leak | src/db/session.py:23 | Wrap the connection in a `with` block so it is closed on every path.
💡 [da-review] · Moderate · Missing migration test | tests/test_migrate.py:1 | Add a test that runs the new migration on a non-empty table.

Not run:
   ❌ 💡 /open-code-review: not ready: no LLM provider configured (ocr llm test failed)

Related tools

  • /da-review — Single-pass adversarial review. One of the default /double-check items; run it alone when one opinion is enough.
  • /clean-code-review — 132 checks across 7 groups. Also a default item; /double-check gives it the same target and folds its findings into the shared list.
  • /iterative-review — Reviews and fixes in a loop. /double-check only lists findings and changes nothing; reach for /iterative-review when you want the problems resolved.
