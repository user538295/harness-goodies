/estimate

← Back to index

Summary

A Story Point size you can check later, measured against your own delivered work. Sizes a brief, plan, task list, epic or single task by comparing it with the features your project has already delivered, and tells you the agent time, tokens and cost that features of that size took.

Every feature's estimate sits next to its real effort — commits, lines added and removed, agent time, tokens, cost — in .estimation.json at the project root. Committing that file is your call; no skill ever commits it.

When to use

You size work by gut feel, and nobody checks afterwards whether the size was right, because the real effort never lands next to the estimate. /estimate keeps both: the Story Points (SP) given before work, and the size judged after delivery from everything that happened.

Mostly it runs by itself. /feature-refinement, /plan-maker, /plan-maker-for-team and /create-tasks estimate the document they write and put a **Story Points:** 8 — estimated 2026-11-04 with /estimate line under its title. /implement adds each task commit to the feature's numbers and re-sizes the feature once every task is ticked. Call it yourself to size a document or to set up the references.

Invocation

/estimate <file.md> [--from <source.md>]
/estimate init

/estimate <file.md> compares the work with the 2–3 closest delivered features (bigger, smaller or the same) and picks an SP from the scale — by default 0, 0.5, 1, 2, 3, 5, 8, 13, 20, 40, 100, 200, 500, 1000. It shows the SP, the closest features with the reason, phases, tasks and estimated hours when the file has them, the expected agent time, tokens and cost, a split suggestion at 40 SP or more, and everything it could not find. Then it saves the item as estimated. --from names the document the file grew out of (the brief of a plan, the team plan of a task list), so that document's entry is updated instead of a second one being created.

/estimate init collects the references: one feature per delivered set of planning documents (brief, plan, tasks file). One sub-agent per feature counts phases, tasks and hours and finds its commits; the main agent then matches the past sessions of all five harnesses to the features in one pass, ranks the features by real size, and proposes an after-delivery SP for each, with 5 as a mid-size feature. You adjust the table before anything is written. Running it again adds newly delivered features and refreshes the actuals; an SP you set is never changed.

Rules that keep the numbers honest:

  • The estimate sharpens with each document: brief, then plan, then tasks file. Each one replaces the feature's SP, so the last estimate before the first task commit, normally the tasks file's, becomes the original SP. A rougher document estimated again after a more detailed one is saved only when you confirm.
  • The original SP freezes at the first task commit; the size judged at delivery goes into updatedStoryPoints. The same number in both means the estimate was right.
  • Only delivered features are references, compared by their after-delivery SP.
  • Sessions are matched by what their prompts name (the feature's documents or task IDs), else by the feature's commit dates, and each match is labelled implement, prompt or dates.
  • Missing data stays empty and is listed in the report — nothing is guessed.
  • With no delivered features yet, you still get an SP, with a warning to run /estimate init.
  • Scales whose sizes can't be added up (emoji, T-shirt sizes) get no split suggestion.

Requirements: Python 3.14 or newer (macOS's built-in python3 is 3.9.6 — install one from python.org or Homebrew). Session numbers come from /session-log; Cursor tokens exist only while session-log's logging is on. When check-jsonschema is installed, every write of .estimation.json is checked against the skill's schema.

Example 1 — Estimating a plan (illustrative example)

Input:

/estimate Documentation/Backlog/csv-import-plan.md

Output / Result:

Story Points: 8

Closest delivered features:
- Bigger than "User avatar upload" (5): two import paths and a validation report instead of one upload.
- Smaller than "Invoice PDF export" (13): no layout engine, no server-side rendering.
- Like "Bulk tag editor" (8): same shape — one parser, one preview screen, one write path.

Plan: 3 phases, 11 tasks, 24.5 estimated hours
Expected effort (features at 8 SP: Bulk tag editor, Report scheduler):
  agent time 260–410 min · tokens 31–58 M · cost $28–$52

Not found:
- no estimated hours on 2 tasks

Saved as "CSV import" (estimated) in .estimation.json

Related tools

  • /feature-refinement and /plan-maker — Estimate the brief and the plan they write; each document keeps the SP of the moment it was written, while .estimation.json holds the latest.
  • /implement — Records every task commit for the feature and triggers the re-size at delivery; .estimation.json stays an uncommitted change.
  • /session-log — The source of agent time, tokens and cost for every session, in all five harnesses.
