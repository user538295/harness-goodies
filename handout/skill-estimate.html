/estimate

← Back to index

Summary

A Story Point size you can check later, measured against your own delivered work. Sizes a brief, plan, task list, epic or single task — calculated from its planned hours at the scale's anchor, or else by a blind comparison with the features your project has already delivered — and tells you the agent time, tokens and cost that features of that size took.

Every feature's estimate sits next to its real effort — commits, lines added and removed, agent time, tokens, cost — in its own file under .harness-goodies/estimations/ at the project root, while the Story Point scale and its anchor live in .harness-goodies/estimation.json. Each file is named after the feature's first day, its ID when it has one, and its name, e.g. 2026-11-04-pm-12-csv-import.json. One file per feature means features estimated on parallel branches no longer cause merge conflicts. Committing .harness-goodies/ is your call; no skill ever commits it.

When to use

You size work by gut feel, and nobody checks afterwards whether the size was right, because the real effort never lands next to the estimate. /estimate keeps both: the Story Points (SP) given before work, and the size judged after delivery from everything that happened.

Mostly it runs by itself. /feature-refinement, /plan-maker, /plan-maker-for-team and /create-tasks estimate the document they write and put a **Story Points:** 8 — estimated 2026-11-04 with /estimate line under its title. /implement adds each task commit to the feature's numbers and re-sizes the feature once every task is ticked. Call it yourself to size a document or to set up the references.

Invocation

/estimate <file.md> [--from <source.md>]
/estimate init
/estimate report [--out <path>]

/estimate <file.md> finds the size on the scale — by default 0, 0.5, 1, 2, 3, 5, 8, 13, 20, 40, 100, 200, 500, 1000 — in one of two ways. When the file has planned hours, the anchor calculates the size from them (see the rules below), and no judge is asked. Otherwise the work is compared once with delivered features: the script picks up to 3 features from every size that holds one, at random but repeatable for the same feature name, and shows them without their SP. Two fresh sub-agents that have seen no SP then judge, each given the same short card for the work and for every pick (name, ID, description, effort, tasks, and planned hours when the anchor is off): the first says whether the work is bigger than, about the same as or smaller than each pick, the second whether each pick, shown in reverse order, is bigger than, about the same as or smaller than the work. The script turns both answers into the size where the work fits: bigger than the picks below it, about the same as that size's picks, smaller than those above; with conflicting answers, the size that contradicts the fewest. When the work fits exactly between two sizes, the one whose picks' planned hours are nearest the work's wins when the work has hours, else the bigger one. So a verdict comes from the work, never from a size already given. It shows the SP, the verdicts, e.g. "bigger than A6 (3), same as C4 (5)", or "calculated from 24.5 h", phases, tasks and estimated hours when the file has them, the expected agent time, tokens and cost, a split suggestion at 40 SP or more, and everything it could not find. Then it saves the item as estimated, with a description (what is built) and an effort (what makes the work big or small: parts changed, new storage or migrations, outside services, unknowns, risky areas; no numbers), each at most 300 characters. --from names the document the file grew out of (the brief of a plan, the team plan of a task list), so that document's entry is updated instead of a second one being created.

/estimate init collects the references: one feature per delivered set of planning documents (brief, plan, tasks file). One sub-agent per feature reads the brief, plan and tasks file together, counts phases, tasks and hours, and returns the feature's description and effort; the main agent then finds every feature's commits in one run over all features, has each commit that only names a feature's ID checked against that feature's name and description, and matches the past sessions of all five harnesses to the features. The main agent alone sizes the features the same way; the verdicts come from blind sub-agent judges that see no SP, at most 8 at a time so the API's rate limit is never hit. Lines changed or commits never decide a size. The first time, it calculates every feature with planned hours from the anchor, then places each other feature among the calculated ones. When nothing can be calculated (the anchor is off, or no feature has planned hours), it asks you to name an example feature for a few sizes — at least one at 13 SP and one small one — and places the rest among those: the only time it waits for you. Later, features with a saved after-delivery SP keep it, and each other feature is calculated, or placed among the saved references. It shows them in one table with the verdicts or "calculated from N h", and saves them right away. Running it again adds newly delivered features and refreshes the actuals; a saved after-delivery SP is never changed.

/estimate report writes one HTML page about your delivered features to .harness-goodies/estimation-report.html (or to --out <path>): how closely the SPs track planned hours, tasks, commits and lines changed, how those numbers grow with the size, where the line counts are inflated (commits counted for several features) and how many lines of committed dependencies, shown but not counted, a feature's commits hold, which features look over- or under-sized next to their actuals, the agent time and cost per feature, and how accurate the estimates made before work turned out. Features that are only estimated so far are shown too, in a different color: in the Pipeline chart, in the feature table and, at their estimated SP, on the plan-based Metric explorer tabs (tasks, hours, phases); no statistic uses them. Every number and sentence on it comes from your data by fixed rules, and Chart.js is bundled inside, so the page opens offline.

Rules that keep the numbers honest:

  • The estimate sharpens with each document: brief, then plan, then tasks file. Each one replaces the feature's SP, so the last estimate before the first task commit, normally the tasks file's, becomes the original SP. A rougher document estimated again after a more detailed one is saved only when you confirm.
  • The original SP freezes at the first task commit; the size judged at delivery goes into updatedStoryPoints. The same number in both means the estimate was right.
  • Only delivered features are references, compared by their after-delivery SP. A comparison never changes a reference's SP, and its verdicts are reported, never saved.
  • Every saved SP comes with its effort text, and a new SP replaces the effort with it, so the effort always explains the SP next to it. Feature files saved before effort existed still load.
  • The scale file holds an anchor, {"sp": 13, "hours": 75} by default (13 SP is about one developer's two-week sprint). It decides the size of a feature with planned hours: the nearest size by ratio (30 h → 5 SP, 60 h → 13 SP), with no judge. The anchor is off when the scale file has none, when it is null or {}, when its hours are null or 0, and on a scale that is not all numbers; then nothing is calculated, and a feature with planned hours is compared like the rest, its hours shown to the judges.
  • Sessions are matched prompt by prompt: a prompt belongs to the feature whose documents or task IDs it names, or whose commits were made while it ran; a follow-up like "go" stays with the prompt before it. A session that worked on three features is split three ways, never counted three times, and nothing is matched by dates. A document, task ID or commit that several features share (every plan's BE-1) counts for none of them.
  • A feature's commits are those that change its planning documents, followed back through moves (a plan archived from Backlog/ to Completed/ keeps its earlier commits), and those a check accepted after reading them against the feature's name and description. An ID never ties a commit on its own: a commit that names the feature's ID is only a candidate, and test(e2e): … is rejected for a feature whose ID is e2e when it is other work. Task IDs link nothing; a commit several features claim, like one that archives several plans, counts for none of them.
  • Lines changed skip committed dependencies: node_modules, vendor, Pods, .venv and similar folders, lockfiles and minified files.
  • Commits and lines changed never decide a size; they are recorded only to check how accurate the estimates were. A delivered feature is re-sized the same way — calculated from its planned hours as delivered, else placed among the saved references — so the sizes stay consistent.
  • Every saved SP records who made it (estimatedBy, updatedBy: the harness and the model), and every session its harness and models; each counted prompt shows its time, its opening text and why it counts.
  • Missing data stays empty and is listed in the report — nothing is guessed.
  • With no delivered features yet, you still get an SP, with a warning to run /estimate init.
  • Scales whose sizes can't be added up (emoji, T-shirt sizes) get no split suggestion.
  • When a merge leaves a name, ID or document in two feature files, every command that reads the feature files names both files, so you can decide which one to keep.

Requirements: Python 3.14 or newer (macOS's built-in python3 is 3.9.6 — install one from python.org or Homebrew). Session numbers come from /session-log; Cursor tokens exist only while session-log's logging is on. When check-jsonschema is installed, every write is checked against the skill's schemas: estimation.schema.json for the scale file, feature.schema.json for a feature file.

Example 1 — Estimating a plan (illustrative example)

Input:

/estimate Documentation/Backlog/csv-import-plan.md

Output / Result:

Story Points: 8

Compared with (two blind judges):
bigger than User avatar upload (5), bigger than Tag filter (5), same as Bulk tag editor (8), same as / smaller than Report scheduler (8), smaller than Invoice PDF export (13)

Effort: a parser for CSV and XLSX files, a new staging table with a migration, a validation report screen; unknown: encodings of customer files.

Plan: 3 phases, 11 tasks, no estimated hours
Expected agent time and cost (features at 8 SP: Bulk tag editor, Report scheduler):
  agent time 260–410 min · tokens 31–58 M · cost $28–$52

Not found:
- no estimated hours on the plan's tasks
- only 2 references at 5 SP
- only 2 references at 8 SP
- only 1 reference at 13 SP

Saved as "CSV import" (estimated) in .harness-goodies/estimations/2026-11-04-csv-import.json

Related tools

  • /feature-refinement, /plan-maker, /plan-maker-for-team and /create-tasks — Estimate the brief, plan, team plan and task list they write; each document keeps the SP of the moment it was written, while the feature's file under .harness-goodies/estimations/ holds the latest.
  • /implement — Records every task commit for the feature and triggers the re-size at delivery; the estimate files under .harness-goodies/ stay uncommitted changes.
  • /session-log — The source of agent time, tokens and cost for every session, in all five harnesses.
