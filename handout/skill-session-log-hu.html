Mi ez

A /session-log az aktuális környezet által átadott prompt- és válaszszöveget helyi Markdown-átiratba írja. Pontosan öt környezetet támogat: Claude Code, Codex, Cursor, OpenCode és OMP.

Mindegyikben ugyanaz az öt parancs használható, de a riportok szándékosan nem egyformák. Az adapterek kizárólag a környezet saját életciklus- és usage-adataiból dolgoznak: a Cursor a fordulónkénti tokenszámokat a hookok adataiban adja át, az átiratokban nem; a Codex a natív rollout rekordokból ad tokenösszeget.

Mit kapsz

  • Olvasható session-átirat. A natív életciklus-eseményekből elérhető promptok, végleges válaszok és alügynök-jelzések időrendben kerülnek egy privát, helyi Markdown-fájlba.
  • Valós natív usage-adatok. A Claude Code és az OMP fordulónkénti adatokat is tud adni; az OpenCode a fő session és az alügynökök natív összesítéseit írja ki; a Codex egy rollout-TOTAL-t ad. A Cursor a stop hook által rögzített tokenszámokból a Claude Code-dal azonos formában ad fordulónkénti sorokat és TOTAL-t, csak a fő ügynökre; az alügynököknél csak a Cursor helyi állapotából vett végső kontextusméret látszik, és ez sosem kerül bele a TOTAL-ba.
  • Idő- és költségadat csak ott, ahol létezik. A Claude Code és a Cursor ugyanabból az ártáblából számol offline árbecslést; az OpenCode és az OMP megőrzi a natív költségmezőket. A Codex tokenmezőket ad ár és munkaidő nélkül.
  • Natív alügynök-elszámolás, ahol elérhető. A Claude Code, az OpenCode és az OMP a saját tárolójában elérhető alügynök-rekordokat is figyelembe veszi. A mezők és a csoportosítás környezetenként eltérnek.
  • Egyértelmű környezetazonosítás. Az univerzális skill az aktuális hostot/modellt kéri meg, hogy válassza ki a claude, codex, cursor, opencode vagy omp azonosítót; útvonalból, folyamatból vagy környezeti változóból soha nem találgat.
  • Helyi és privát. A kezelt naplófájlok 600 jogosultságúak, és a csomag semmit nem tölt fel.

A pontos címkék: Claude Code, Codex, Cursor, OpenCode és OMP. Cél megadása nélkül a usage azt a sessiont összesíti, amelyben éppen dolgozol: az aktuális projekt felső szintű sessionjei közül azt választja, amelyikben a legfrissebb felhasználói prompt van, így egy párhuzamosan még író session sosem kerül kiválasztásra; az OMP és az OpenCode /session-log parancsa közvetlenül a saját sessionjét adja át. Más session riportjához adj meg sessionazonosítót, illetve ahol az adapter elfogadja, átirat-útvonalat. Az OpenCode csak azonosítót vagy --latest-et fogad el. A --check kizárólag Claude Code alatt használható, és a telepített ccusage eredményével vet össze.

Jó tudni

  • Nincs külön telepítés. A csomagot minden környezet pluginja magával hozza. Egy repómásolatból a bash skills/session-log/install.sh --harness cursor --arguments "status" a másolat saját csomagjával futtatja a status parancsot; semmit nem másol sehova.
  • Az aktiválás környezetenként külön történik. Az on, az off, a status és a repair csak a megadott azonosítót érinti. Az on — restart required után indítsd újra a környezetet. Codexnél az on parancshoz a user538295 marketplace-ről telepített codex-goodies plugin kell: a ~/.codex/hooks.json fájlba felvett parancsok csak ennek a marketplace-nek a legfrissebb telepített codex-goodies csomagját futtatják. Engedélyezd őket a /hooks alatt, ami a futó sessionben azonnal érvénybe lép, vagy indítsd újra a Codexet, és ha megjelenik a Hooks need review képernyő, válaszd a Trust all and continue lehetőséget. A codex exec és a többi nem interaktív futás nem mutat jóváhagyó képernyőt, és csak a már engedélyezett hookokat futtatja, ezért egyszer engedélyezd őket az interaktív felületen (TUI). A szövegük nem nevez meg csomagútvonalat vagy verziót, így a plugin frissítése nem változtat rajta, és a hookok engedélyezettek maradnak, amíg a bejegyzéseik a helyükön maradnak a hooks.json-ban. A status a futásidejű jelölőt a futó csomag VERSION értékével veti össze, ezért a plugin skilljéből futtasd: egy eltérő VERSION-ű repómásolatból továbbra is az utasítást írja ki.
  • A Claude Code plugin birtokolja a hookjait. A hooks/hooks.json mindig regisztrálja őket, és semmit nem csinálnak, amíg az on létre nem hozza a bekapcsoló fájlt; az on és az off semmit nem regisztrál (az on a régi maradványok tisztítása után létrehozza ezt a kapcsolót, az off törli, a futásjelzőkkel együtt), a status pedig csak olvas. Ez a kiadás csak a pluginon keresztül regisztrál hookot; egy olyan másolat, amelyet a tisztítás kénytelen volt megtartani (lásd lent), elveszíti a változatlan SKILL.md fájlját, így a Claude Code már nem tölti be skillként; tedd félre. A korábbi kiadások a ~/.claude/settings.json-ban regisztrálták a hookokat, és a csomagot a ~/.claude/skills/session-log alá másolták, amely a pluginfrissítések után elavult; az on, a repair és a Claude Code minden indítása eltávolítja ezeket a maradványokat (és azokat a régi prompt_log szkripteket, amelyeket a plugin előtti telepítés a ~/.claude/scripts alá másolt), és az eltávolításuk miatt a status sosem kér újraindítást; ha a tisztítás meghiúsul, amit legacy cleanup failed: <ok>; fix it, then run repair formában jelez, vagy átmeneti okból (75-ös kilépési kód) kimarad, amit legacy cleanup skipped: <ok> formában jelez, az on a naplózást akkor is bekapcsolja. Session-log hooknak számít minden parancs, amely SESSION_LOG_OWNER=universal-session-log előtaggal kezdődik, a plugin saját hooks/hooks.json parancsának másolata, és bármely bash …/skills/session-log/adapters/claude/claude_hook.sh <esemény> parancs; a natív Windows C:\ útvonalat is felismeri, de a törléséhez WSL kell. A másolat csak akkor törlődik, ha a tulajdonosi manifeszt minden fájlját változatlannak igazolja; különben a repair megnevezi, hogy félretehesd. Egy indítás csak akkor ismétli meg a tisztítást, ha a legutóbbi kísérlet óta megváltozott a settings.json, a session-log csomag (a helye vagy a VERSION fájlja), vagy az, hogy létezik-e még az a másolat vagy azok a szkriptek; csak az átmeneti hibával végződő (75-ös kilépési kód) vagy egy jelzés által befejezése előtt leállított kísérlet nem kerül feljegyzésre, ez a következő indításkor újra lefut, a sikertelen kísérletet (például egy módosított régi szkript miatt) viszont feljegyzi, és csak akkor fut újra, ha ezek közül valami megváltozik, a hibát pedig a repair mutatja meg. A többi hook érintetlen marad. A Cursor is importálja az engedélyezett Claude Code pluginokat, és futtatja a hookjaikat; ott csak a sessionindításkori hook takarítja a régi maradványokat, egyik sem naplóz, és nem is ír vagy töröl Claude futásjelzőt (egy megtartott, a settings.json-ban még regisztrált régi példány régebbi kódja ezt megteszi, amíg félre nem teszed).
  • A Cursor plugin is birtokolja a hookjait. A .cursor-plugin/hooks.json a Cursor saját formátumában regisztrálja őket (a cursor-goodies plugin nem a Claude Code hooks/hooks.json fájlját használja); minden session-indításnál, promptnál, válasznál, leállásnál és alügynök-leállásnál lefutnak, felhasználói megerősítés nélkül. A Cursor a hookparancsokat a $SHELL -c-ddel futtatja; sh, bash, zsh és fish alatt teszteltük őket, a más szintaxisú shellekkel (például nushell, xonsh vagy PowerShell) minden eseménynél hibára futnak, és ezt a Cursor csak a Cursor Settings → Hooks alatt rögzíti (értesítés nélkül). Minden parancs előbb a bekapcsoló fájlt ellenőrzi, így kikapcsolt naplózásnál a plugin hookjai azonnal kilépnek Python indítása nélkül (a régi ~/.cursor/hooks.json-bejegyzések a tisztításig továbbra is a régebbi kódot futtatják), és akkor is csendben kilépnek, ha a plugin hookszkriptje vagy a python3 hiányzik. A natív Windows nem támogatott ezekhez a hookokhoz, mert ott a Cursor PowerShell-lel futtatja őket: használd a Cursort WSL alatt. A Cursor csak akkor tölti be a pluginhookokat, ha a Cursor Settings → Include Third-Party Plugins, Skills, and Other Configs be van kapcsolva (alapértelmezés), és a szerveroldali plugin-import kapcsoló is engedi; ha a naplózás be van kapcsolva, de a telepített cursor-goodies verzió egyetlen hookja sem futott még, a status ezt írja: on — no hook of this cursor-goodies version has run. A status csak azokat a hookokat veszi figyelembe, amelyek csomagjának VERSION-je megegyezik az őt futtató session-log skillével, a sikertelen hookfuttatások pedig a Cursor Settings → Hooks alatt látszanak. A korábbi kiadások a ~/.cursor/hooks.json-ban regisztrálták a hookokat, és a csomagot a ~/.cursor/skills/session-log alá másolták; a Cursor mindkét hookforrást futtatja, ezért az on és a repair eltávolítja ezeket a session-log bejegyzéseket (a többi hook marad), a másolatot, ha a tulajdonosi manifest minden fájlját változatlannak igazolja (különben a repair megnevezi: az a megtartott másolat, amelynek a SKILL.md fájlja is módosult, továbbra is régebbi kódot futtat, amely használatkor újra beírja a bejegyzéseit a ~/.cursor/hooks.json-ba, ezért tedd félre), és a régi adapter-állapotfájlokat. Bekapcsolt naplózásnál minden Cursor session-indítás lefuttatja a repair-t, ha a ~/.cursor/hooks.json még tartalmaz ilyen bejegyzést, legfeljebb 20 másodpercig; az időtúllépést vagy azt, ha a tisztítás el sem indul, a hook stderr kimenetére írja, amelyet a Cursor naplóz.
  • Az omp plugin birtokolja a bővítményét. A plugin package.json-ja regisztrálja (omp.extensions); semmit nem naplóz, amíg az on létre nem hozza a bekapcsoló fájlt, és minden promptnál újraolvassa ezt a kapcsolót; az on és az off semmit nem regisztrál: az on a régi maradványok tisztítása után létrehozza ezt a kapcsolót, az off törli, a betöltött bővítmény futásjelzőjét pedig meghagyja. Betöltéskor ettől függetlenül megírja a futásjelzőjét és elindítja a régi maradványok tisztítását; áthelyezett vagy symlinkelt omp-gyökéren (például egy elnevezett profilnál) csak a /session-log parancsot regisztrálja, és az jelzi a hibát; a /reload-plugins nem tölti újra a bővítményeket, ezért a plugin telepítése vagy frissítése után indítsd újra az omp-t (addig az on és a status on — restart required választ ad). A frissítés előtt indult session tovább működik; a /session-log parancsához viszont újra kell indítani az omp-t, ha a betöltött csomag eltűnt, és nincs hozzá felhasználói szintű telepítés linkelve, vagy ha a tisztítás törölte. A korábbi kiadások a ~/.omp/agent/extensions/session-log.js linket a ~/.omp/agent/skills/session-log alá másolt csomagba irányították; az omp ezt a bővítményt a pluginé mellett is betöltené, ezért az on, a repair és minden omp-indítás (a háttérben) eltávolítja őket, a másolatot csak akkor, ha a tulajdonosi manifeszt minden fájlját változatlannak igazolja. Egy omp-indítás ezt a tisztítást a csomag (a helye vagy a VERSION-je) vagy a meglévő maradványok minden változása után egyszer futtatja, és minden kísérletét feljegyzi a ~/.omp/agent/session-log/legacy-cleanup.stamp fájlba, kivéve az átmeneti hibával végződőt (75-ös kilépési kód) és azt, amelyik nem futott végig (120 másodperc után időtúllépéssel leállt, leállították, vagy el sem indult): ez a következő indításkor újra lefut; a sikertelen kísérletet is feljegyzi, és csak akkor fut újra, ha ezek közül valami megváltozik. A frissítés utáni első omp-indítás még egyszer betölti a régi bővítményt is; a kettő ugyanazokat a duplikációmentes bejegyzéseket írja. A háttérben futó tisztítás hibája (az átmeneti nem), illetve egy általa megtartott csomagmásolat egyszer az omp stderr kimenetére kerül, a félbemaradt kísérlet pedig minden olyan indításkor, amely újrapróbálja; az okát a /session-log repair nevezi meg. Amíg a régi másolat megvan, a /skill:session-log arra is mutathat, ezért a /session-log parancsot használd.
  • Az OpenCode plugin is maga birtokolja a kezelőit. Az opencode-goodies csomag setupja regisztrálja a /session-log parancsot, a prompt hookot és az eseményfolyam-feldolgozót, amelyek semmit nem csinálnak, amíg az on létre nem hozza a bekapcsoló fájlt; az on és az off semmit nem regisztrál (az on a régi maradványok tisztítása után létrehozza ezt a kapcsolót, az off törli, a futásjelzőkkel együtt), a status pedig csak olvassa, a plugin által bekapcsolt naplózás alatt (betöltéskor és minden promptnál) írt futásjelzővel együtt. A /session-log közvetlenül a csomag CLI-jét futtatja, a kimenetét pedig értesítésként mutatja a sessionben, amelyet a modell a következő promptoddal együtt lát. A korábbi kiadások a ~/.config/opencode/plugins alá linkeltek egy adaptert, amelyet az OpenCode V2 minden indításkor megpróbál betölteni, de elutasít, és egy markdown /session-log parancsot telepítettek, amely felülírja a pluginét; az on, a repair és a plugin setupja (telepített csomagonként egyszer, helye vagy VERSION-je szerint, és újra, ha ilyen maradvány megjelenik vagy eltűnik; az átmeneti hibával (75-ös kilépési kóddal) végződő vagy félbemaradt (120 másodperc után időtúllépéssel leállt, leállított vagy el sem indult) kísérlet a következő indításkor újra lefut; a sikertelent feljegyzi, és a repair megmutatja) eltávolítja ezeket és a régi csomagmásolatot. Ami ott nem bizonyíthatóan a session-logé, megmarad; egy idegen commands/session-log.md nevét kiírja, hogy félretehesd.
  • A bekapcsolt adapter helyreáll magától. Codexben bekapcsolt naplózásnál a status és a usage a hiányzó vagy elavult hooks.json bejegyzéseket újratelepíti, előtte pedig lefuttatja a régi maradványok tisztítását.
  • A usage nem közös séma. A Claude Code fordulónkénti és alügynök-összesítést ad offline árbecsléssel; az OpenCode és az OMP a natív token- és költségadatokat őrzi meg; a Codex ár nélkül összegzi a rollout tokenrekordjait; a Cursor pedig a Claude Code formájában mutatja azokat a tokenszámokat, amelyeket a stop hook bekapcsolt naplózás mellett, a plugin hookjaival rögzített — csak a fő ügynökre, mert a subagentStop nem ad tokenadatot —, az alügynököknél csak a Cursor helyi állapotából vett végső kontextusméretet írja ki (ez nem kerül bele a TOTAL-ba), és egyértelmű hibával leáll, ha egy sessionhöz nincs rekord.
  • A függőségek parancsonként eltérnek. Az on, az off és a repair bash-t és Python 3-at igényel; az adaptertelepítéshez és a régi maradványok tisztításához shasum vagy sha256sum is kell; a futásállapot ellenőrzéséhez és a Claude Code-hoz jq szükséges. Az OpenCode usage ezenfelül sqlite3-at, az OMP riportja pedig Bunt igényel. A ccusage csak a Claude Code --check opcionális függősége. Natív Windowson csak a Claude Code plugin hookjai futnak (Git Bash alatt, kikapcsolt naplózásnál jq nélkül); az on, az off, a repair és a sessionindításkori tisztítás WSL-t igényel. Amíg a korábbi kiadások maradványai megvannak, natív Windowson egy indítás megkísérli ezt a tisztítást, és a kísérlet csendben meghiúsul; mint minden sikertelen kísérletet, ezt is feljegyzi, így csak akkor fut újra, ha a settings.json, a csomag vagy azok a maradványok megváltoznak.
  • Csak az alapértelmezett gyökerek támogatottak. Ezek: ~/.claude, ~/.codex, ~/.cursor, ~/.config/opencode (a natív adatok helye ~/.local/share/opencode) és ~/.omp/agent. Az áthelyezett gyökerek egyértelmű hibával leállnak.

Hogy néz ki egy naplózott forduló

Helyzet: egy teljes forduló — elküldesz egy promptot, egy háttér-al-ügynök befejeződik, az asszisztens válaszol, és az előző forduló óta modellt és effortot váltottál. Ez kerül a session-fájlba (Claude Code, ~/.claude/prompt-logs/<projekt>/session_….md):

## 14:02:11

Implement the next uncompleted task in plans/FEAT-001.md

---

14:03:05 sub-agent finished: general-purpose (agent-9f3c2a1b), jsonl: /Users/…/<sid>/subagents/agent-9f3c2a1b.jsonl

### 14:05:53 response

<az asszisztens végleges üzenete, szó szerint>

working time: 00:03:42
est. used token: input: 2000, output: 1000, cache_create: 150000, cache_read: 0, total_tokens: 153000, price: $2.32, model: claude-opus-5, effort: max
switched: model claude-sonnet-5 → claude-opus-5, effort high → max

---

Fentről lefelé olvasva: a prompt, majd a lefutott al-ügynök, majd a válasz, majd a mérések. A total_tokens = input + output + cache-írás + cache-olvasás. Az itteni switched: sor magyarázza a nagy cache_create-et: a modellváltás teljes cache-írást kényszerített ebben a fordulóban.

Ilyen a Claude Code usage riportja

Parancs: /session-log usage Claude Code alatt (az aktuális sessiont összesíti — a projekt azon sessionjét, amelyben a legfrissebb felhasználói prompt van). A többi környezet megtartja a fent leírt saját riportformáját.

Claude Code: usage

1. 14:02:11  Implement the next uncompleted task…   est. used token: … price: $2.32
2. 14:12:40  Fix the failing test in auth_test…      est. used token: … price: $0.41
   sub-agent general-purpose (agent-9f3c2a1b)         est. used token: … price: $0.77

TOTAL (2 requests, 1 sub-agent)  input: … output: … total_tokens: …  price: $3.50

Fordulónként egy számozott sor, al-ügynökönként egy sor a sessionben talált átiratokból, majd egy összevont TOTAL. Minden átirat egyszer számít, bármilyen mélyen ágyazódnak az al-ügynökök.
