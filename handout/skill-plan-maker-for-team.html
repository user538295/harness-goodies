/plan-maker-for-team

← Back to index

Summary

One reviewable plan that tells frontend, backend and tester exactly what they own — grounded in your real code, not guesses. Turns a feature brief into a single Markdown team plan with a layered architecture, Given/When/Then scenarios, logical contracts between roles, Mermaid diagrams, a test-level allocation table and a documentation checklist.

Before writing anything it investigates the codebase and docs with nine read-only subagents, then one synthesis subagent writes the plan from their findings. The output is <feature-name>-team-plan.md in the same folder as the brief. It contains no tasks: the task-by-task breakdown is a separate downstream step, /create-tasks.

When to use

A feature needs several people, and each of them has to know which layer, which contract and which tests are theirs — without one long plan that mixes everyone's work. /plan-maker-for-team keeps a fixed Frontend, Backend and Tester section, tags each role-owned heading (#frontend-role, #backend-role, #tester-role) so you can filter one role's whole scope, for example in Obsidian, and puts every boundary two roles must honour into a numbered contract.

Trigger phrases (from the SKILL.md):

  • "turn a feature brief or a feature request into an actionable engineering plan that splits work across frontend, backend, and tester roles"
  • the user provides a brief file (often named like feature-name-brief.md)
  • "plan a feature for the team"
  • "make a team plan"
  • "organize multi-role work" — even if they do not say the word plan

It sits between /feature-refinement (writes <feature>-brief.md) and /create-tasks (writes <feature>-tasks.md), which /implement then executes. For a single developer who wants a plan with tasks in one file, use /plan-maker instead.

Invocation

/plan-maker-for-team <feature-name>-brief.md

Step 0 — the brief gate. The brief must answer five questions with concrete sentences, not a placeholder or one vague word: Problem (the user problem), Goal (the end state after it ships), Core Flow (the main step-by-step user path), In Scope and Out of Scope. If the input is only a short feature request, or any of the five is missing or weak, the skill does not plan: it tells you the brief is insufficient and runs /feature-refinement to produce the brief first. It never invents the missing product intent.

What happens next:

  1. Set up. It announces the architecture approach — Clean Architecture by default (Presentation → Use Cases → Interface Adapters → Entities → Frameworks & Drivers) — and the contract tooling it will use, then creates a work directory <feature-name>-plan-work/ beside the brief.
  2. Investigate. Nine read-only subagents run in parallel: contracts, scenarios, backend-architect, frontend-architect, data-schema, adr, docs, tester, structured-output. Each reads code first and docs second, cites real file paths and symbols, modifies nothing, and writes only its own findings file into the work directory.
  3. Synthesize. One synthesis subagent reads the findings and writes the plan, then adds a **Team plan:** back-link to the brief's ## References section and rewrites any bare project file path in the plan's prose as a Markdown link.
  4. Estimate. The synthesis subagent ends by running /estimate <plan> --from <brief> and writing **Story Points:** <SP> — estimated <YYYY-MM-DD> with /estimate under the plan's title. A failed estimate is reported and leaves the line out.
  5. Report and clean up. You get the summary — status, open-question count, which diagrams were included or deferred, link warnings — and the work directory is deleted.

Rules the plan always follows:

  • Three role sections, always. A role with no work keeps its section, marked N/A.
  • Under Clean Architecture, Presentation maps to frontend and the other four layers to backend; the tester is cross-cutting.
  • Unit and integration tests belong to the implementing developer; the tester owns e2e and manual tests only. Each scenario is allocated to the cheapest test level that proves it.
  • Scenarios cover happy, unhappy, edge and non-functional paths. IDs S# (scenarios), C# (contracts) and Q# (questions) are never renumbered on later edits.
  • No code: real components are named, never implemented. Every name comes from the investigation; anything unconfirmed becomes an open question.
  • Status is draft while any open question remains, then planned → in-progress → done.
  • A Documentation update checklist lists the real docs the feature touches, each with a reason: new feature, contradiction with code or no change needed.

Your own architecture. Ask for a specific architecture skill (for example dotnet-vsa-webapi) and the plan uses that skill's approach and its structure units as layers instead of Clean Architecture. If the named skill cannot be found, it stops and asks you — it never falls back silently.

Optional: TypeSpec contracts. The skill runs tsp --version; exit 0 means TypeSpec is available. Then internal seams become core-construct .tsp files beside the plan, each validated with tsp compile <file> --no-emit, and HTTP/API seams become TypeSpec HTTP services in an api-contracts/ subfolder, each emitting a <contract>.openapi.yaml through the @typespec/openapi3 emitter. If the OpenAPI libraries cannot be installed, it writes a core-construct .tsp without YAML and says so. Without TypeSpec, each contract is written inline as a short logical summary.

Example 1 — Planning from a complete brief (illustrative example)

Input:

/plan-maker-for-team multi_sound_playback-brief.md

Output / Result: multi_sound_playback-team-plan.md beside the brief, shortened:

---
id: MSP
feature: Multi-Sound Simultaneous Playback
brief: multi_sound_playback-brief.md
status: draft        # draft (open questions remain) → planned → in-progress → done
roles: [frontend, backend, tester]
architecture: clean
---

# MSP · Multi-Sound Simultaneous Playback — Team Plan
**Story Points:** 8 — estimated 2026-11-04 with /estimate

**How to read this file**
- **Architecture approach:** Clean Architecture — the default fallback; no override skill was requested.
  **Layers:** Presentation · Use Cases · Interface Adapters · Entities · Frameworks & Drivers.
- **Contracts** are logical here, in the **built-in fallback** form — this feature has no client↔server API ...
- **Tasks** are not in this file — task breakdown is a separate downstream step that consumes this plan.

## Background · Goal · Scope · Acceptance criteria · What does NOT change · Known limitations
## Approach & architecture
### Architecture        (Mermaid flowchart: AudioService *(mod)*, AVAudioPlayerPool *(new)* ...)
### Actors & Use Cases · ### Flows · ### Prior decisions · ### Contradictions

## Contracts / seams
**C2 — Audio control**  *(Presentation ↔ Use Case / Adapter)*
The start use case receives the **whole selected set**; the audio service then owns play / stop /
pause / resume / volume for the entire pool, exposed through `AudioServiceProtocol`. ...

## Scenarios #tester-role
| **S6** | **Given** sounds playing · **When** a call/notification interrupts · **Then** all players pause,
and all resume when it ends |

## Frontend — Presentation (SwiftUI) #frontend-role
## Backend — Entities · Use Cases · Adapters · Frameworks (Swift) #backend-role
## Tester #tester-role
| S5, S6 | manual |

## Documentation update
- [ ] [audio.md](./Documentation/Architecture/audio.md) — *new feature* — update for the player-pool change (if present)

## Open questions
| **Q3** | tests | Can interruption (S6) be automated in our harness, or must it stay a manual test? ... |

## References
- **Brief:** [multi_sound_playback-brief.md](./multi_sound_playback-brief.md)

The brief gains a - **Team plan:** [multi_sound_playback-team-plan.md](./multi_sound_playback-team-plan.md) bullet under its ## References heading. The plan stays draft because Q3 is still open.

Example 2 — A short feature request (illustrative example)

Input:

/plan-maker-for-team Let users play several sleep sounds at once

Output / Result:

The brief is insufficient: this is a short feature request, not a brief.
Problem, Goal, Core Flow, In Scope and Out of Scope are not answered.

Running /feature-refinement to produce multi-sound-playback-brief.md ...

/feature-refinement asks its clarifying questions and writes the brief. Once the brief exists, planning continues from the investigation step, as in Example 1 — the missing product intent comes from you, never from the planner.

Related tools

  • /feature-refinement — Writes the <feature>-brief.md this skill needs; the brief gate sends you there when the input is thin.
  • /create-tasks — Breaks the team plan into <feature>-tasks.md and appends a **Tasks:** link to the plan's References section.
  • /plan-maker — A single-developer plan with the tasks in the same file, instead of a role-split plan.
  • /estimate — Sizes the plan after it is written and updates the brief's feature file under .harness-goodies/estimations/ rather than adding a second one.
  • /iterative-review — Stress-tests the finished plan with parallel devil's-advocate review-fix loops.
