/vertical-slicer

← Back to index

Summary

Something a user can see working on day one, then one more behavior per slice — never "database first, UI last". Breaks a feature into an ordered list of vertical slices: each delivers one user-observable behavior end-to-end, and the first is a walking skeleton — the thinnest behavior that runs through every layer it needs.

Agents drift into horizontal slicing (schema, then API, then UI, then "wire it all up"), because layered code is what they have seen most and splitting by layer is mechanically easy. This skill tests every slice against a four-part verticality test and a smell list, and re-slices any slice that fails. It works with whatever layering the project already uses — Clean Architecture layers, MVC tiers, feature folders, client/server, services — and needs no other skill.

When to use

Your plan for a feature reads "set up the schema, build the API, build the screens, integrate" — and nothing can be demoed until the last step. /vertical-slicer turns the same feature into increments where each one ships a working behavior.

Trigger phrases (from the SKILL.md description) — use it when you want to:

  • break a feature, story, epic, or initiative into increments
  • slice work for delivery
  • order delivery phases
  • avoid layer-by-layer (horizontal) slicing or a "set up the foundation first" plan

/create-tasks also uses it, when installed, to set the vertical-slice phases of a task breakdown.

Invocation

/vertical-slicer <feature description>

The skill takes no flags. Describe the feature; the skill then runs six steps:

  1. Load the rules from references/vertical-slicing.md: the verticality test, the smell list, the behavior-first order and the cut-thinner toolkit.
  2. List behaviors, not components — "the user can now X" or Given/When/Then; never layers, services, screens or files.
  3. Pick the walking skeleton (slice 1) — the thinnest behavior that runs end-to-end and produces something a user sees. It carries the minimal data/model foundation inside that behavior, never as a separate setup phase.
  4. Order the rest by user value and hard dependency, thinnest-viable first.
  5. Map each behavior down into tasks across the layers it needs — only after the slices exist — to confirm each slice is end-to-end.
  6. Self-check and re-slice in a loop until every slice passes, then run a plan-level check over the whole list.

The verticality test — all four must hold:

  • Demoable — a Given/When/Then that a non-developer recognizes as the feature's intended user doing a thin but real instance of the feature. An admin or diagnostic action that only exercises new infrastructure does not count.
  • End-to-end — every layer the behavior needs does its real job; a stubbed layer does not count.
  • Independently shippable — delete every other slice and this one still delivers value to the intended user.
  • Named as an outcome — verb + object ("Reserve a seat"), never a layer or tech noun.

Passing the four is not enough: any one smell sends the slice back for re-slicing. The smells: a layer/tech-noun title (Database, Schema, Models, Backend, API, Endpoints, UI, Frontend, Infrastructure, Setup, Scaffold, Plumbing, Integration, Wiring), a single-layer slice, the foundation-first trap, infrastructure-in-costume, a spike shipped as a deliverable, a slice that proves nothing, a terminal integrate phase, a layer-ordered sequence, sacrificial-proxy ordering, a stub-floor (Potemkin) layer, and an over-built skeleton.

Plan-level check: every slice must advance the feature you actually asked for. Leading slices that deliver a different, lower-value feature mainly to force shared infrastructure into existence are foundation-first in disguise; the skill reorders so slice 1 is the thinnest real instance of the requested feature.

Cutting a slice thinner never splits it by layer. The rule: find the biggest source of variation in the behavior and reduce it to one. SPIDR names five ways to do that:

  • Spike — a time-boxed investigation only to learn; never a shippable slice.
  • Paths — one path now, others later (pay by card now; Apple Pay later).
  • Interfaces — one client, format or device now (web now; mobile later).
  • Data — one data subset now (domestic addresses now; international later).
  • Rules — the core business rule now, edge rules later.

Output: an ordered slice list, walking skeleton first. Each slice has a Title (verb + object), a Behavior (Given/When/Then), Layers touched (the end-to-end path through the project's actual structure) and Verticality (the four tests and the smell check, all marked pass). No "setup/foundation" slice and no closing "integrate" slice may appear.

Example 1 — Slicing in-app notifications (illustrative example)

Input:

/vertical-slicer In-app notifications: users receive, view, mark-as-read, and configure delivery preferences for activity notifications (mentions, replies, system alerts).

Output / Result:

1. See a mention notification in the bell   (walking skeleton)
   Behavior:      Given Bob mentions Alice in a comment, When Alice opens the app,
                  Then she sees one unread "Bob mentioned you" in her bell dropdown with a badge of 1.
   Layers touched: event → persisted Notification → API → bell UI
                  (carries the minimal Notification model inside the behavior)
   Verticality:   demoable ✓ · end-to-end ✓ · shippable ✓ · outcome-named ✓ · smells: none

2. Mark a notification as read
   Behavior:      Given an unread notification, When Alice clicks it, Then it loses unread
                  styling, the badge drops 1→0, and it stays read after refresh.
   Layers touched: bell UI → API → stored read state
   Verticality:   demoable ✓ · end-to-end ✓ · shippable ✓ · outcome-named ✓ · smells: none

3. Get notified of a reply
   Behavior:      Given Carol replies to Alice's thread, When Alice opens the app,
                  Then a "Carol replied" notification appears alongside her mentions.
   Layers touched: reply event → persisted Notification → API → bell UI
   Verticality:   ... all pass — a second event type as its own slice,
                  not an "add all event types" phase

4. Mute reply notifications
   Behavior:      Given Alice turns off "Replies" in settings, When Carol replies, Then no
                  notification is created and the bell is unchanged; mentions still arrive.
   Layers touched: toggle UI → stored preference → suppression at creation
   Verticality:   ... all pass — a preference delivered end-to-end, not a "settings layer"

Example 2 — Catching a horizontal checkout plan (illustrative example)

Input:

Slice our checkout plan: a shopper reviews a cart, enters shipping + payment, and places an order that charges a card and emails a receipt.
1. Set up the checkout database schema and models
2. Build the payment-gateway integration layer
3. Implement the checkout REST API endpoints
4. Build the checkout UI screens
5. Integrate and wire up the full checkout flow

Output / Result:

Self-check — every slice fails:
- 1 Schema and models   → foundation-first trap + layer-noun title
- 2 Integration layer   → layer-noun title; proves no scenario
- 3 REST API endpoints  → single-layer slice + layer-noun title
- 4 UI screens          → single-layer slice + layer-noun title
- 5 Integrate / wire up → terminal integrate phase (proves 1–4 were horizontal)

Re-sliced by behavior, one source of variation at a time (Paths, then the rest later):
1. Place a free order for one in-stock item   (walking skeleton: no payment, no email;
   carries the minimal Order/OrderLine model inside the behavior)
2. Charge a card and place a paid order       (adds the payment gateway end-to-end)
3. Reject a declined card without creating an order   (failure path as its own slice)
4. Ship a paid order to a captured address
5. Email a receipt for a placed order
...

The result is a working order on day one, grown one behavior at a time, instead of four disconnected layers that demo nothing until a final "wire it all up".
