/session-log

← Back to index

What it is

/session-log writes the prompt and response text exposed by the current harness to a local Markdown transcript. It supports exactly five host identities: Claude Code, Codex, Cursor, OpenCode, and OMP.

The same five commands control every harness, but their reports are deliberately not identical. Each adapter uses only its native lifecycle and usage records: Cursor exposes per-turn token counts in hook payloads but not in transcripts, while Codex exposes token totals through native rollout records.

What you get

  • A readable session transcript. Native lifecycle events append available prompts, final responses, and sub-agent notices in chronological order to a private local Markdown file.
  • Truthful native usage. Claude Code and OMP can report per-turn usage; OpenCode reports native main-session and sub-agent aggregates; Codex reports a native rollout TOTAL. Cursor reports per-turn lines and a TOTAL in Claude Code's format from the token counts its stop hook recorded, for the parent agent only; each sub-agent shows only its final context size from Cursor's local state, never added to TOTAL.
  • Native timing and cost where available. Claude Code and Cursor calculate an offline price estimate from the same price table; OpenCode and OMP preserve their native cost fields. Codex reports token fields without price or working-time figures.
  • Native sub-agent accounting where available. Claude Code, OpenCode, and OMP include the sub-agent records their stores expose. Report fields and grouping remain harness-specific.
  • An explicit identity boundary. The universal skill asks the current host/model to select claude, codex, cursor, opencode, or omp; it never infers identity from paths, processes, or environment variables.
  • Local and private. Managed log files use 600 permissions and nothing is uploaded by this package.

Run /session-log with one of these. With no argument it defaults to status.

The exact labels are Claude Code, Codex, Cursor, OpenCode, and OMP. Without a target, usage reports the session you are working in: among the current project's top-level sessions it picks the one with the newest user prompt, so a parallel session that is still writing output is never chosen; OMP's and OpenCode's /session-log commands pass their own session directly. Pass a session ID, or a transcript path where that adapter accepts one, to report another session. OpenCode accepts only an ID or --latest. Claude Code alone accepts --check to compare with ccusage when installed.

Good to know

  • Nothing to install separately. Each harness plugin ships the package. From a checkout, bash skills/session-log/install.sh --harness cursor --arguments "status" runs status through that checkout's package; nothing is copied anywhere.
  • Activation is per harness. on, off, status, and repair touch only the explicitly selected identity. Restart after on — restart required. For Codex, on needs the codex-goodies plugin from the user538295 marketplace: the commands it adds to ~/.codex/hooks.json run only that marketplace's newest installed codex-goodies package. Approve them in /hooks, which takes effect in the running session, or restart Codex and choose Trust all and continue if it shows the Hooks need review screen. codex exec and other non-interactive runs show no review screen and run only hooks already trusted, so trust them once in the interactive TUI. Their text names no package path or version, so plugin updates never change it, and they stay trusted as long as the entries keep their place in hooks.json. status compares the runtime marker with the running package's VERSION, so run it through the plugin's skill: from a checkout with another VERSION it keeps reporting the instruction.
  • The Claude Code plugin owns its hooks. Its hooks/hooks.json always registers them, and they do nothing until on creates the enable flag; on and off only flip that flag, and status only reads. This release registers hooks only through the plugin; a copy the cleanup had to keep (see below) loses its unchanged SKILL.md, so Claude Code no longer loads it as a skill; move it aside. Older releases registered the hooks in ~/.claude/settings.json and copied the package to ~/.claude/skills/session-log, which went stale after plugin updates; on, repair, and each Claude Code startup remove those leftovers (and the legacy prompt_log scripts the pre-plugin install copied into ~/.claude/scripts), and removing them never makes status report a restart; on still turns logging on when that cleanup fails (and names the failure) or is skipped because another session-log command is running. A session-log hook is any command that starts with SESSION_LOG_OWNER=universal-session-log, a copy of the plugin's own hooks/hooks.json command, or any bash …/skills/session-log/adapters/claude/claude_hook.sh <event> command; a native Windows C:\ path is recognized too, but removing it takes WSL. The copy goes only when its ownership manifest proves every file in it unchanged; otherwise repair names it so you can move it aside. A startup repeats the cleanup only when settings.json, the session-log package (its location or VERSION), or the presence of that copy or those scripts changed since its last successful attempt; a failed attempt, for example one skipped because another session-log command holds the install lock, runs again at the next startup. Other hooks stay untouched. Cursor imports enabled Claude Code plugins and runs their hooks too; there only the session-start hook runs the legacy cleanup, and none of them logs, nor writes or removes Claude runtime markers (a kept legacy copy still registered in settings.json runs older code that does, until you move it aside).
  • The Cursor plugin owns its hooks too. .cursor-plugin/hooks.json registers them in Cursor's own format (the cursor-goodies plugin does not use the Claude Code hooks/hooks.json); they fire on each session start, prompt, response, stop, and sub-agent stop, and run with no prompt. Cursor runs the hook commands with your $SHELL -c; they are tested with sh, bash, zsh, and fish, and shells with another syntax (for example nushell, xonsh, or PowerShell) fail on every event, which Cursor records only in Cursor Settings → Hooks (no notification). Each command checks the enable flag first, so while logging is off the plugin's hooks exit immediately without starting Python (legacy ~/.cursor/hooks.json entries still run the older code until the cleanup removes them), and they also exit silently when the plugin's hook script or python3 is missing. Native Windows is not supported for these hooks, since Cursor runs them through PowerShell there: use Cursor under WSL. Cursor loads plugin hooks only while Cursor Settings → Include Third-Party Plugins, Skills, and Other Configs is on (the default) and its server-side plugin import gate allows it; when logging is on but no hook of the installed cursor-goodies version has run, status reports on — no hook of this cursor-goodies version has run. status counts only hooks of the same package VERSION as the session-log skill it runs from, and failing hook runs are listed in Cursor Settings → Hooks. Older releases registered the hooks in ~/.cursor/hooks.json and copied the package to ~/.cursor/skills/session-log; Cursor runs both hook sources, so on and repair remove those session-log entries (other hooks stay), the copy when its ownership manifest proves every file unchanged (otherwise repair names it: a kept copy whose SKILL.md itself changed still runs older code that re-registers its ~/.cursor/hooks.json entries whenever it is used, so move it aside), and the adapter state files older releases wrote. Each Cursor session start while logging is on runs repair when ~/.cursor/hooks.json still holds such entries, for at most 20 seconds; a timeout, or a cleanup that cannot start, is written to the hook's stderr, which Cursor logs.
  • The omp plugin owns its extension. The plugin's package.json registers it (omp.extensions); it logs nothing until on creates the enable flag and reads that flag at every prompt, so on and off only flip it. It still writes its runtime marker and starts the legacy cleanup when it loads; on a relocated or symlinked omp root (for example a named profile) it only registers /session-log, which reports the error; /reload-plugins does not reload extensions, so restart omp after installing or upgrading the plugin (until then on and status report on — restart required). A session started before an upgrade keeps working; its /session-log needs an omp restart once the package it loaded is gone and no user-scope install is linked for it, or once the cleanup removed it. Older releases linked ~/.omp/agent/extensions/session-log.js into a package copy seeded at ~/.omp/agent/skills/session-log; omp would load that extension beside the plugin's, so on, repair, and each omp start (in the background) remove them, the copy only when its ownership manifest proves every file in it unchanged. An omp start runs that cleanup once per change of the package (its location or VERSION) or of the leftovers present, and stamps it in ~/.omp/agent/session-log/legacy-cleanup.stamp only after a success: a failed attempt, or one skipped because another session-log command holds the install lock, runs again at the next start, and a kept copy is reported once. The first omp start after upgrading still loads the legacy extension once; both write the same deduplicated entries. The background cleanup reports a failure (not a busy lock), or a package copy it kept, on omp's stderr; /session-log repair names the cause. While a seeded copy remains, /skill:session-log may resolve to that old copy, so use /session-log.
  • The OpenCode plugin owns its handlers too. The opencode-goodies package's setup registers /session-log, the prompt hook, and an event-stream consumer, which do nothing until on creates the enable flag; on and off only flip that flag (on runs the legacy cleanup first, off clears the runtime marker), and status only reads it with the runtime marker the plugin writes while logging is on (when it loads, and with each prompt). /session-log runs the package's CLI directly and shows its output as a notice in the session, which the model sees with your next prompt. Older releases linked an adapter into ~/.config/opencode/plugins, which OpenCode V2 tries to load at every start and rejects, and installed a markdown /session-log command that overrides the plugin's; on, repair, and the plugin's setup (once per installed package, its location or VERSION, and again when such a leftover appears or goes; only a successful attempt counts, so a failed one, including one skipped because another session-log command holds the install lock, runs again at the next start) remove them and the seeded package copy. A file there that is not provably session-log's stays; a foreign commands/session-log.md is named so you can move it aside.
  • Enabled adapters recover automatically. In Codex, while logging is enabled, status and usage reinstall missing or outdated hooks.json entries before continuing, running the legacy cleanup first.
  • Usage is not a common schema. Claude Code reports per-turn and sub-agent totals with offline price estimates; OpenCode and OMP preserve native token and cost data; Codex totals native rollout token records without price; Cursor uses Claude Code's layout for the parent agent's token counts that its stop hook recorded while logging was on with the plugin's hooks (subagentStop carries no tokens), lists each sub-agent with only its final context size from Cursor's local state (not added to TOTAL), and fails explicitly when a session has no records.
  • Dependencies are command-specific. on, off, and repair need bash and Python 3; adapter installs and the legacy cleanup also need shasum or sha256sum; runtime-state checks and Claude Code need jq. OpenCode usage additionally needs sqlite3; OMP usage needs Bun. ccusage is optional for Claude Code's --check. On native Windows only the Claude Code plugin's hooks run (under Git Bash, without jq while logging is off); on, off, repair, and the session-start cleanup need WSL. While older releases' leftovers remain, every native startup attempts that cleanup, and the attempt fails silently.
  • Default roots only. The roots are ~/.claude, ~/.codex, ~/.cursor, ~/.config/opencode (with native data in ~/.local/share/opencode), and ~/.omp/agent. Relocated roots fail explicitly.

What a logged turn looks like

Scenario: one full turn — you submit a prompt, a background sub-agent finishes, the assistant answers, and you had switched model and effort since the previous turn. This is what lands in the session file (Claude Code, ~/.claude/prompt-logs/<project>/session_….md):

## 14:02:11

Implement the next uncompleted task in plans/FEAT-001.md

---

14:03:05 sub-agent finished: general-purpose (agent-9f3c2a1b), jsonl: /Users/…/<sid>/subagents/agent-9f3c2a1b.jsonl

### 14:05:53 response

<the assistant's final message, verbatim>

working time: 00:03:42
est. used token: input: 2000, output: 1000, cache_create: 150000, cache_read: 0, total_tokens: 153000, price: $2.32, model: claude-opus-5, effort: max
switched: model claude-sonnet-5 → claude-opus-5, effort high → max

---

Reading top to bottom: the prompt, then the sub-agent that ran, then the reply, then the measurements. total_tokens is input + output + cache-write + cache-read. The switched: line here explains the large cache_create: changing models forced a full cache write on this turn.

What a Claude Code usage report looks like

Command: /session-log usage in Claude Code (totals the current session — the project's session with the newest user prompt). Other harnesses keep their native report shapes described above.

Claude Code: usage

1. 14:02:11  Implement the next uncompleted task…   est. used token: … price: $2.32
2. 14:12:40  Fix the failing test in auth_test…      est. used token: … price: $0.41
   sub-agent general-purpose (agent-9f3c2a1b)         est. used token: … price: $0.77

TOTAL (2 requests, 1 sub-agent)  input: … output: … total_tokens: …  price: $3.50

One numbered line per turn, one line per sub-agent transcript found under the session, then a merged TOTAL. Every transcript is counted once, no matter how deeply sub-agents nest.
