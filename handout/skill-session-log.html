What it is

/session-log archives each session's prompts and responses as a per-project Markdown log, with a saved token and price report beside it. One bundled Python script, session_log.py (with its sessionlog/ package folder), does all the work for exactly five host identities (a harness is the coding tool that hosts the skill): Claude Code, Codex, Cursor, OpenCode, and OMP.

Logging is opt-in: it stays off until you run on. While it is on, the commands read the harness's own session data and write the archive; nothing is written while it is off, and the archive is written when a command or a session start syncs, not live while you type.

What you get

  • One log and one report per session. Every session with activity since you turned logging on gets a Markdown log (each prompt and its reply, with local time and UTC offset) and a plain-text usage report beside it. Both are rewritten whole when the session changes. Once a session has activity after on, it is archived whole, including prompts from before on; off does not hide earlier prompts either: when a session continues after a later on, the prompts typed while logging was off are archived with it. Cursor is the exception: it archives only what its hooks recorded while logging was on.
  • The same report in every harness the skill runs in. Per prompt (a request in the report): working time, input, output, cache-write (cache_create) and cache-read tokens, an estimated price, the models and the effort levels used. Prices come from the bundled prices.json, except where the harness records a cost itself (OMP, OpenCode), which is used as recorded; Codex and Cursor prices are labelled API-equivalent.
  • Sub-agents are counted. Each sub-agent gets its own line and its tokens and price are part of the TOTAL. Cursor is the exception: it keeps no sub-agent tokens, so its report covers the main session only and its price is marked incomplete.
  • Usage for a session that was never archived. usage computes the same report live from the harness's data, which must still exist, and saves nothing, for example for a session with no activity since on.
  • An explicit identity boundary. The skill tells the model to take the identity (claude, codex, cursor, opencode, or omp) from the host's runtime context; the script never infers it from paths, processes, or environment variables.
  • Local and private. Log folders are created with 700 and log files written with 600 permissions. Nothing is uploaded by this package.

The four commands

Run /session-log with one of these. With no argument the skill runs status. Any other argument is refused.

usage takes at most one argument. Without one, or with --latest, it reports the project's session with the newest prompt, among the archived top-level sessions of the project you are in, or failing that of its nearest parent folder that has sessions (the archive is read first; only when the project has no archived session is the harness's data read, and then the session whose source file is newest wins). With a session ID it reports that session: an exact ID, else the unique session whose ID starts with what you typed. A session ID holds only letters, digits, _ and -.

The script prints failures on stderr as session-log: messages and exits 0 on success, 1 on a runtime error and 2 on bad arguments.

How to invoke it in each harness

HarnessInvocationObserved
Claude Code /session-log <args> or /claude-goodies:session-log <args> Both ran the script in claude -p. The plugin's session-start hook also syncs while logging is on.
Codex $session-log <args> A typed /session-log is plain text in codex exec. The workspace-write sandbox refused writes to ~/.codex/prompt-logs until approved, so approve that write for on. Codex has no hooks: its sessions are archived by the next on, status or usage.
Cursor /session-log <args> Ran the script in cursor-agent -p, which fires no prompt hooks and so records nothing. The form in the Cursor app has not been observed.
OMP /skill:omp-goodies/session-log <args> Use the namespaced form: the plain /skill:session-log ran an older copy from the Claude plugin cache when Claude Code's plugin registry listed claude-goodies (observed on omp 18.12.6). OMP has no hooks: its sessions are archived by the next on, status or usage.
OpenCode In prose, for example "use the session-log skill with status"; the plugin registers no /session-log command The model reaches the skill through OpenCode's skill tool (observed with opencode run on an earlier release). That the shipped SKILL.md makes the model run the script end to end in OpenCode has not been observed. The script run directly printed a correct report once: python3 <skill dir>/session_log.py opencode usage. OpenCode has no hooks: its sessions are archived by the next on, status or usage.

On native Windows every harness is not yet tested; the maintainer runs skills/session-log/tests/windows-checklist.md on a real Windows PC after the release.

Good to know

  • Nothing to install separately. Each harness plugin ships the script. From a checkout, run it directly: python3 skills/session-log/session_log.py claude status (the identity is claude, codex, cursor, opencode or omp).
  • Dependencies. macOS or Linux (native Windows is not yet tested), and Python 3.14 or newer as python3; with an older python3 commands fail with a message and hooks do nothing. The script uses only the Python standard library: no bash, jq, sqlite3 command, Bun, Node or zstd is needed to run it. Bash is needed only for the skill's optional locator block, and Cursor's hook launcher is a POSIX shell script.
  • Where the files go. The log root is <harness root>/prompt-logs: ~/.claude, ~/.codex, ~/.cursor, ~/.config/opencode or ~/.omp/agent (default roots only; a relocated root such as CLAUDE_CONFIG_DIR or CODEX_HOME fails the command). A session's files are <log root>/<project folder>/session_<UTC time>_<id>.md and .usage.txt. Times inside carry a UTC offset in local time; the time in the file name is UTC.
  • When it archives. on, status and usage sync while logging is on; off syncs once and then stops it. Hooks only start a sync or record events: Claude Code's plugin hook syncs at session start; Cursor's plugin hooks record each prompt and response and sync at session start. Codex, OMP and OpenCode register no hooks.
  • Cursor keeps no readable session store. Its hooks write one record per event under <log root>/.records/, so only prompts recorded while logging was on are archived; status says so when no record exists since on. Cursor may also run the Claude Code hook of an imported claude-goodies plugin; whether the Cursor app does is not yet verified, nor is how long a chat start waits for it, whether the hook file stays executable after a marketplace install, or the install-cache layout.
  • Upgrading from an older release. Older releases copied the package into the harness's skill root and registered hooks in the harness's own files, and a newer plugin does not remove them. on and status list what they find under Old-release leftovers (not deleted):, each with a one-line fix, and delete nothing. For an old file or folder the fix is a ready command, mkdir -p <harness root>/session-log-old/... && mv <old path> <harness root>/session-log-old/..., which moves it outside every skills folder; moving a copy elsewhere inside a skills folder may still load it. For ~/.claude/settings.json, ~/.codex/hooks.json or ~/.cursor/hooks.json the fix says which entries to delete by hand: every entry under hooks whose command starts with SESSION_LOG_OWNER=universal-session-log or runs an old session-log script (the fix line names the script paths), keeping the others. Until a seeded copy is moved aside it may be loaded in place of the plugin's skill. Old-format logs stay beside the new ones, so a few sessions that span the upgrade can appear twice (an old-format log plus a new log).
  • What else differs from the older release.
    • Upgrade gap. The new on-time is the time of the first new command or hook, not the old flag's age. On Codex, OMP and OpenCode, which have no hook, sessions between the plugin update and the first new on, status or usage are not archived. Claude Code and Cursor run the migration at session start.
    • An old seeded copy cannot switch the new logging. Its own off and status read and delete only the old .enabled flag, not the new .log_enabled: while it shadows the skill, off changes nothing and status shows off while the new logging stays on. Move it aside first.
    • A leaner Markdown log. It holds the header, each prompt and each response. The old per-response working time:, est. used token: and switched: lines, the sub-agent finished entries, the **Session file:** and **Resume:** header lines and the --- separators are gone. The usage report beside it holds model, effort, tokens, time and price per prompt.
    • usage takes a session id or --latest, not a transcript path. usage /path/to/transcript.jsonl fails with "no session has the id". Old Cursor token files are not read, so a session recorded only by the older release cannot be reported.
    • Cursor sub-agents. The report lists only sub-agents with a recorded stop (type and time, tokens "not recorded by Cursor"); the old roster and final context: N tokens sizes read from Cursor's own database are gone.
    • Cursor hook records are raw and kept. Each file under <log root>/.records/ holds the raw hook input, including user_email, transcript_path and the prompt and reply text. Files are 0600 in a 0700 folder, and nothing ever prunes them.
    • Python older than 3.14 keeps the hooks silent. The Claude Code and Cursor hooks then exit without writing anything or printing a message; for Cursor only status hints at it ("no hook events"), and the commands themselves fail with a message.
  • Prices. They come from skills/session-log/prices.json, except where the harness records a cost itself. A request with no rate is never priced as $0: its row shows unknown (or ≥ $X (incomplete) when only part of it has a rate), and the TOTAL then shows ≥ $X (incomplete); a problem with the file is shown by status as Price file problem:.

What a log and its report look like

Scenario: two prompts in one Claude Code session; the first one started a sub-agent. Logging is on, and the next status archived the session. The log is ~/.claude/prompt-logs/shop-<12 hex digits>/session_2026-10-21_12-02-11_7c1e4d52-3b8a-4f60-9d21-5a6b7c8d9e01.md (the time in the name is UTC; the session is a made-up sample run through the real script in a sandbox; its project path, project-folder hash, dates and clock times are edited for the page, the rest is the script's output):

# Session log
- harness: claude
- session: 7c1e4d52-3b8a-4f60-9d21-5a6b7c8d9e01
- project: /Users/you/shop
- start: 2026-10-21 14:02:11 UTC+2

## 2026-10-21 14:02:11 UTC+2
Implement the next uncompleted task in plans/FEAT-001.md

### 2026-10-21 14:05:53 UTC+2 response
Task 1 is implemented and its tests pass.

## 2026-10-21 14:12:11 UTC+2
Fix the failing test in auth_test

### 2026-10-21 14:12:51 UTC+2 response
The assertion compared against a stale fixture; fixed.

Reading top to bottom: a header, then for each prompt its time and text and, when it got an answer, the reply's time and text. Tokens, prices and sub-agents are not in the log; they are in the report beside it.

What a usage report looks like

Command: /session-log usage in the project of that session. It prints the saved .usage.txt beside the log, byte for byte (same edits as above):

session: 7c1e4d52-3b8a-4f60-9d21-5a6b7c8d9e01
harness: claude
project: /Users/you/shop
times: UTC+2

1. 14:02:11 (working time 00:03:42) "Implement the next uncompleted task in plans/FEAT-001.md"
est. used token: input: 2000, output: 1000, cache_create: 150000, cache_read: 0, total_tokens: 153000, price: $0.78, model: claude-opus-5-5, effort: max
2. 14:12:11 (working time 00:00:40) "Fix the failing test in auth_test"
est. used token: input: 3000, output: 800, cache_create: 0, cache_read: 40000, total_tokens: 43800, price: $0.02, model: claude-sonnet-5-5, effort: high

sub-agent: Explore (agent-9f3c2a1b), working time: 00:02:00
est. used token: input: 20000, output: 3000, cache_create: 0, cache_read: 0, total_tokens: 23000, price: $0.04, model: claude-haiku-4-5, effort: -

TOTAL (2 requests, 1 sub-agents)
working time: 00:04:22
est. used token: input: 25000, output: 4800, cache_create: 150000, cache_read: 40000, total_tokens: 219800, price: $0.84, model: claude-haiku-4-5+claude-opus-5-5+claude-sonnet-5-5, effort: high+max

One numbered row per prompt (clock time under the offset in the header, the prompt's first 60 characters), one block per sub-agent, then the TOTAL. total_tokens is input + output + cache-write (cache_create) + cache-read. The total's working time is the sum of the prompts' only, its price the sum of the rows shown, and its models and efforts those of every row, sorted and joined with +; - means none was recorded.

The same layout serves every harness. In Cursor each sub-agent shows tokens: not recorded by Cursor, the total carries tokens: main session only — Cursor does not record sub-agent tokens, and the TOTAL price reads ≥ $X (incomplete). Codex and Cursor prices end with (API-equivalent). usage --latest and usage <session-id> print the same report for the session they name.
