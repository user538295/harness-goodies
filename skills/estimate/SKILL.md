# /estimate

Sizes planned work in Story Points (SP) relative to the project's delivered features, and keeps every feature's estimate next to its real effort. All data lives under `.harness-goodies/` at the **project root** (`git rev-parse --show-toplevel`, else the current directory): the scale and its anchor in `estimation.json`, written with the defaults by the first save and the user's to edit from then on, and one file per feature in `estimations/`, so features estimated on parallel branches never touch the same file. Only the bundled script `estimate.py` writes the feature files — never edit them by hand. Committing `.harness-goodies/` is the user's job.

`estimate.py` needs **Python 3.14 or newer**. macOS's stock `python3` is 3.9.6: if the script reports a too-old Python, tell the user to install Python 3.14+ from python.org or Homebrew and stop.

4. **`$SESSION_DIR`** is the working directory your host reports for this session in its runtime/system context (the folder the session was started in), taken verbatim. `estimator` and `record-commit` read the newest session of that folder, which is the session running now; the project's own folder can hold a newer session of another run when you work on a project from a session started elsewhere.

Run every command below **from the user's repository**, never from `$BASE`. JSON output goes to stdout. - `read` prints `{"version", "scale", "anchor", "features"}`: the scale and its anchor and every feature file in name order, each feature with its `file` name (the default scale and anchor and no features when there are none); `--references` keeps only the delivered features with an after-delivery SP — the only features ever used for comparison.
- The scale file's `anchor` (`{"sp": 13, "hours": 75}` by default: 13 SP is about one developer's two-week sprint) ties an SP to a number of planned hours, and it decides the SP of every feature with planned hours: `anchor <estimatedHours>` gives it, with no judge (see "Find the size"). It is off when the scale file has none, or it is null, `{}`, or its `hours` is null or 0, and on a scale that is not all numbers. Without the anchor nothing is calculated: a feature with planned hours is compared like every other feature, its hours shown on its card. An anchor of another shape, with negative hours, or whose `sp` is not a value of the scale above 0 fails every command (`cannot read .harness-goodies/estimation.json`): tell the user to fix the file.
- A feature's file is `<first day>[-<id>]-<name>.json` in lowercase ASCII (e.g. `2026-11-04-pm-12-csv-import.json`); the id and name parts are cut when long. The first day is set when the file is created: the earliest of the day git first added each of its docs, the creation day of each doc not committed yet, the day of its first commit, and today. A changed name or id renames the file; its first day never changes.
- Every command that reads the files names on stderr each name, id or doc that two feature files share, e.g. `duplicate name 'X': 2026-10-01-x.json, 2026-10-02-x.json` (usually after two branches were merged); ids are compared by their file-name form, so `PM-12` and `pm-12` are the same id. A shared name or id means one file is a leftover copy: report it with both files and ask the user which one to keep; `remove <file>` deletes the other. A doc listed by two features on purpose (e.g. one plan for two features) may stay. Under `/implement` (`record-commit`, possibly headless) only report the duplicates; never ask or block. A command whose own feature is ambiguous fails, naming both files.
- `save` upserts one feature from a partial entry (pass JSON with `-` on stdin). It targets the feature whose `sources.docs` shares a path with the entry's, else the one with the same `name`, else creates one (`name`, `description` and `effort` are then required). Given fields replace stored ones, except: `storyPoints` and `estimatedAt` freeze once the feature is `in-progress` or `delivered`, a non-null `updatedStoryPoints` never changes, a null `plan` count never overwrites a known one, and a missing or null `id` never erases a stored one (a different `id` replaces it with a warning). `estimatedBy` is saved with `storyPoints` and `updatedBy` with `updatedStoryPoints` (either without its size is refused): each records who made that size and follows it, so it freezes or stays with the size, and a new size saved without one clears it. Names and ids are unique: a save is refused when it would give its feature a name or id another feature already holds (a name or id already shared is only warned about), and an id without a letter or digit is refused. SPs must be values of the `scale`. `sources.docs` are merged; `git` replaces `git` and `sources.commits` together; given `sources.sessions` replace the stored ones; `usage` totals are always recomputed from the sessions.
- `description` and `effort` are two texts of at most 300 characters each (what they say: "Find the size"); `check-text` checks them. `save` refuses (exit 2, nothing written) an entry whose own `description` or `effort` is over 300 characters or empty, or whose `effort` has a digit; number words are not digits, and digits in `description` are allowed. Texts already stored are never re-checked, so saves without texts and `record-commit` still work on older features. A save that creates a feature or carries `storyPoints` or `updatedStoryPoints` needs an `effort` in the same entry, else it is refused (`a size needs its effort`); the effort is replaced together with the SP, so it always explains the SP saved with it. When the save ignores its SP (a frozen `storyPoints`, or an `updatedStoryPoints` already set; both still warn), the stored effort stays, and the given one is stored only when the feature has none yet. Every other write needs no effort: a save without a size, and `record-commit`. Feature files saved before `effort` existed still load and take those writes; they get an effort with their next size or the next `init`.
- `remove <file>` deletes one feature's file, named as `read` shows its `file`.
- `find-sets` (no arguments; `init` step 1) lists the project's planning docs and groups them into one set per feature. A planning doc is a `.md` file named `…brief.md`, `…team-plan.md`, `…plan.md` or `…tasks.md` (after `-`, `_` or nothing): inside git the tracked and untracked-not-ignored files, outside git a walk that skips hidden and dependency folders. Docs join one set when they share a folder and a stem (the name before `[-_]<kind>.md`, in any case), when a front matter `brief:`, `team-plan:`, `plan:` or `tasks:` value names the other (relative to the doc, else to the project root, else by basename in the doc's folder), or when they share a folder and the same first `# ` heading (without a `Feature Brief:` label and a ` — Team Plan`, ` — Task Breakdown`, ` — Plan`, ` — Tasks` or ` — Brief` suffix). Links in the text, such as a References section, never join docs: they cite other features. It prints `{"sets": [{"docs", "planDoc", "plan", "delivered", "missing"}], "missing"}`: `planDoc` is the set's doc holding tasks (a tasks file before a team plan before a plan), `plan` its `doc-stats` as `{"phases", "tasks", "completed", "estimatedHours"}` or null, `delivered` true when every task of it is ticked. A set's `missing` names a front matter value not found (`<doc>: front matter <key>: <value> not found`), several task lists (`several task lists: <a>, <b>`; the first by path is taken), the planDoc's `doc-stats` lines prefixed `<basename>: `, and `no plan or tasks file with tasks`; the top-level `missing` names a failed file listing. An argument is a bad argument; an unreadable doc fails the command (`cannot read <path>: …`).
- `doc-stats` counts phases, tasks and ticked tasks (through `/implement`'s `plan-progress.sh`) and sums the `· <n>h` task estimates. When it fails on a document, work the counts out by reading the document and say so.
- `check-text` checks a `description` and an `effort` before they are saved (`/estimate` step 6, `init` step 2). Its input is `{"description", "effort"}`, at least one of them, each a string; any other key or a non-string is a bad argument. It prints `{"problems": [...]}`, `[]` when the texts pass, in this order: `description has N characters (at most 300)`, `effort has N characters (at most 300)`, `effort has digits: <word>, <word>` (each word holding a digit 0–9, once), `<field> is empty`. Rewrite the texts until `problems` is empty: `save` refuses the same problems.
- `git-stats` and `match-sessions` take the same input, all features at once: `{"features": [{"name", "id", "docs", "taskIds", "commits"}]}`. `commits` is optional: the full hashes a check accepted for that feature (see `/estimate init` step 4); a short hash, or one not reachable from HEAD, fails the command naming it and the feature. A doc path, doc basename, task ID or commit that more than one feature lists is evidence for none of them (every plan reuses `BE-1`), which only one global view can tell.
- `git-stats` gives each feature `{"name", "commits", "count", "linesAdded", "linesRemoved", "candidates"}`. Its commits are those that change one of its docs, followed back through moves and copies (a plan archived from `Backlog/` to `Completed/` keeps the commits made before the move), plus its given `commits`. An ID never ties a commit: `candidates` (`[{"hash", "subject"}]`, oldest first, `subject` being the message's first line) lists the commits whose subject or body names the feature's `id`, in any case, that no feature claims (`[]` without an id); they count only once checked and passed back as `commits`. One commit can be a candidate of several features; accepted for more than one, it counts for none. Task IDs find no commit. A commit that several features claim, such as one that archives several plans, counts for none and is no candidate; stderr names those commits. Lines changed skip committed dependency files (`node_modules/`, `vendor/`, `Pods/`, `.venv/` and similar folders, lockfiles, `.min.js`/`.min.css`).
- `match-sessions` reads the past sessions of all five harnesses (session-log `list`, then `usage` with its per-prompt rows) and gives each feature its slice of a session, prompt by prompt: a prompt belongs to the features its text names, else to the feature(s) with the most commits made while it ran; a prompt with neither follows the prompt before it (earlier prompts the first match); a sub-agent follows the prompt it started under. Each slice is a session entry with the session's `harness`, the `models` its counted prompts and sub-agents ran on, and in `prompts` each counted prompt: its `number` (the row of `session-log usage`), `at`, its first 60 characters as `text`, and the `reason` it counts (`names <doc or task ID>`, `made <n> of its commits`, `follows prompt <n>` or `before prompt <n>`). The slice's numbers are those rows' sums, so a session that worked on three features is split three ways, never counted three times. Nothing is matched by dates. `missing` names failed calls, sessions without prompt rows (counted whole, `prompts: null`) and, per feature, commits made while no prompt of a listed session ran (made by hand, or in sessions whose transcripts are gone). Each feature also has `usage`, exactly what `save` stores as `usage` for those sessions and that `matchedBy`: `{"matchedBy", "sessions", "agentTimeMinutes", "tokens": {"input", "output", "reasoning", "cacheRead", "cacheWrite", "total"}, "costUsd"}`; a total is null when any session lacks that number or there is no session.
- `record-commit` adds one task commit to its feature (see "Record a commit"); its lines skip committed dependency files, as in `git-stats`.
- `estimator` prints `{"estimator": {"harness", "models"}, "missing"}`: the harness given and the models session-log names for the last prompt of that harness's latest session in `--session-dir` (the project root without it), which is the prompt running now. A `--session-dir` that is not a folder fails the command. `models` is null, with the reason in `missing`, without `--session-log` or when that prompt names no model. Run it once before the run's first save of an SP and send its `estimator` value unchanged with every SP the run saves: as `estimatedBy` with `storyPoints`, as `updatedBy` with `updatedStoryPoints`.
- `anchor <hours>` prints `{"hours", "sp", "missing"}`: the value of the scale that `<hours>` planned hours give at the anchor, the nearest by ratio (13 SP = 75 h makes 30 h 5 SP and 60 h 13 SP). `sp` is null, with the reason in `missing`, when the anchor is off. Hours that are not a number above 0 are a bad argument.
- `calculate` sizes every feature with planned hours at once (`init` step 6). Its input is `{"features": [{"name", "id", "description", "effort", "tasks", "estimatedHours"}]}`, the features' cards; an unknown key, a missing or duplicate `name`, `estimatedHours` that are not a number above 0 or null, or `tasks` that are not an integer of 0 or more or null is a bad argument. It prints `{"features": [{"name", "hours", "sp", "missing"}], "pool": [...]}` in input order: `sp` is what `anchor <estimatedHours>` gives; it is null with `missing: ["no planned hours"]` without hours, and null with the anchor's reason when the anchor is off. `pool` holds the features with an `sp`, each `{"name", "id", "description", "effort", "sp", "tasks", "estimatedHours"}`, ready to pass as `neighbours`' and `place`'s `pool`.
- `neighbours` picks the features to compare a feature with (see "Find the size"). Its input is `{"name": <feature name>, "pool": [...]}`: `pool` is optional, each item `{"name", "id", "description", "effort", "sp", "tasks", "estimatedHours"}`, and takes the place of the references (`read --references`, each with its `updatedStoryPoints` as `sp` and its plan's tasks and hours); the first `init` gives its calculated features or the user's examples there, because nothing is saved yet. It prints `{"picks", "groups", "missing"}`. `picks` is what the judges see: up to 3 features from every scale value that holds a pool feature, each `{"name", "id", "description", "effort", "tasks", "estimatedHours"}`, in name order, without its SP. `groups` holds `{"sp", "names"}` for every value that holds picks, in scale order, `names` being that value's picks. The feature itself (same name) is never a pick. The picks are random but repeatable: seeded by the feature's name, so the same feature always gets the same picks and a renamed one new picks. `missing` names each value with fewer than 3 (`only 1 reference at 20 SP`), each empty value between the smallest and the biggest held one (`no reference at 13 SP`), each pick without an effort (`no effort for '<name>'`), and an empty pool (`no reference to compare with`). A request that is not a JSON object, has no `name`, has any other key (`unknown field '<key>'`), a `pool` that is not a list, or a pool item without a `name` or with an `sp` off the scale, is a bad argument; a scale that is not all numbers fails the command (`neighbours needs a numeric scale`).
- `place` turns the judges' verdicts into the size (see "Find the size"). Its input is `{"name", "pool", "hours", "verdicts", "pickVerdicts"}`: `name` and the optional `pool` as given to `neighbours`, whose picks it recomputes; `hours` the feature's planned hours, a number above 0, or null or absent; `verdicts` the first judge call, the feature against each pick, and `pickVerdicts` the second, each pick against the feature, both `{"<pick name>": "bigger" | "same" | "smaller"}` naming every pick exactly once. It prints `{"sp", "tie", "report", "verdicts", "missing"}`. `sp` is the size where the feature fits: bigger than the picks below it, about the same as that size's picks, smaller than those above; with conflicting answers the size contradicting the fewest; a tie goes to the size whose picks' planned hours are nearest the feature's when it has hours, else up. The sizes tried run from one scale step below the smallest picks to one step above the biggest, values without picks included; the hours break a tie only when every tied size has picks with planned hours, nearest by ratio. `sp` is null when there is no pick. `tie` is null, or `{"between": [a, b], "by": "hours" | "round up"}`, `a` and `b` the lowest and the highest tied size. `report` names each pick by its id (its name without one) with its SP, in scale order, e.g. `bigger than S (5), same as / smaller than M-1 (8)`, "X / Y" marking a pick whose two calls disagree; `verdicts` holds `{"name", "id", "sp", "verdict", "pickVerdict"}` per pick, in scale order; `missing` holds `neighbours`' lines. A request that is not a JSON object, has no `name` or has any other key (`unknown field '<key>'`), a `pool` as `neighbours` refuses it, `hours` that are not a number above 0 or null, and a verdict map that misses a pick (`verdicts: missing '<name>'`), names another (`verdicts: unknown '<name>'`) or uses another word (`pickVerdicts: '<word>' for '<name>'`) are bad arguments, each message naming its map; a scale that is not all numbers fails the command (`place needs a numeric scale`).
- `report` writes one self-contained HTML page (data, findings and the bundled Chart.js inline, so it opens offline in any browser) from the references and their commits in git, to `--out <path>` (relative to the working folder) or by default `.harness-goodies/estimation-report.html`. Every number and sentence on it comes from the data by fixed rules. It prints `{"report", "features", "forecasts", "missing"}`: the page's path, how many references it analyses, how many of them had an estimate made before work (`storyPoints`), and the commits they list that git does not hold. It fails, writing nothing, when the scale is not all numbers or there is no reference.

## Find the size

Every SP this skill saves — by `/estimate <file.md>`, by `init` and by the re-size after delivery — is found here, in one of two ways. A feature with planned hours is **calculated** from them while the anchor is on; every other feature is **compared** once with delivered features picked from every size that holds one, so sizes stay consistent from run to run and from person to person. The script picks the features to compare with and turns the verdicts into the size; two judges who have seen no SP give the verdicts, so each comes from the work, never from a size already given. No size is ever decided by lines changed or commits, and a comparison never changes a reference's SP. Each step that runs it gives the feature's planned hours (none when it has none) and, in the first `init` only, a `pool`.

1. **Calculated.** When the feature has planned hours and the anchor is on, run `anchor <estimatedHours>`: its `sp` is the size, with no judge. Report "calculated from N h".
2. **Compared.** Otherwise run `neighbours` with `{"name": "<feature name>"}` (plus the step's `"pool"`). Start two fresh sub-agents as judges (inline, by you, only when the harness has no sub-agent tool); in `init`, run at most 8 judges at once, so the API's rate limit is never hit.
   - Each judge gets the feature as a card in the same fields as the picks — `name`, `id`, `description`, `effort`, `tasks`, and `estimatedHours` only when the feature has hours and the anchor is off — and `neighbours`' `picks` exactly as printed: never an SP, `groups` or `missing`.
   - **Call 1**, the first judge: the feature against each pick, the picks in printed order. It returns `{"<pick name>": "bigger" | "same" | "smaller"}`, the feature against that pick.
   - **Call 2**, the second judge: each pick against the feature, the picks in reverse order. It returns `{"<pick name>": "bigger" | "same" | "smaller"}`, that pick against the feature.
   - Size means total build effort; lines changed and commits are never evidence.

   Then run `place` with `{"name": "<feature name>", "hours": <planned hours or null>, "verdicts": <call 1>, "pickVerdicts": <call 2>}` (plus the same `"pool"`): its `sp` is the size.
3. **No pick and nothing calculated** (`neighbours` prints no `picks`): give your own estimate from the feature's documents, and open the report with `/estimate` step 1's warning.
4. Report `place`'s `report`, e.g. "bigger than A6 (3), same as C4 (5)", its `tie` when not null (e.g. "between 5 and 8, by hours"), and its `missing` lines as missing data. The verdicts are reported, never saved.

**`description` and `effort`** are written from the feature's documents, at most 300 characters each. `description`: what was built. `effort`: what makes the work big or small — the number of parts changed, new storage or migrations, outside services, unknowns, risky areas — with no numbers, because `neighbours` returns tasks and hours itself. Run `check-text` on them and rewrite them until its `problems` is empty: `save` refuses a given text over 300 characters or an effort with a digit; number words are not digits, and texts already stored are never re-checked. Every document that can be sized gives an effort: a brief's problem, goal and scope name the drivers coarsely, and the plan and the tasks file sharpen the text the same way they sharpen the SP. The effort always explains the SP saved with it. Example from archon-search's A6 brief: "Two concurrency fixes: a lock around the indexing-state store's read-modify-write on every write path, including sync's reset, and a cache-invalidation call on the router. No new storage. Risk: proving no lost writes under concurrent syncs."

## `/estimate <file.md> [--from <source.md>]`

`--from` names the document a planning skill started from (the brief of a plan, the team plan of a task list). Both documents go into `sources.docs`, so the save updates that document's entry instead of creating a second one.

**The estimate sharpens with each document.** A feature's documents add detail in order: the brief, then the plan or team plan, then the tasks file. Each is estimated when it is written, and each save replaces the feature's SP. So the estimate saved last before the first task commit, normally the tasks file's, becomes the frozen original `storyPoints`: the one the accuracy check compares with the delivered size. Each document keeps the SP line it was written with, so a brief can show 8 while its tasks file shows 13.

1. Run `read --references`. When it lists no feature, still estimate, but open the report with: **"Warning: no delivered features to compare with — this estimate is not based on past work. Run `/estimate init`."**
2. Read `<file.md>` and run `doc-stats <file.md>`. Note the feature's own ID when the document shows one: in its title, its front matter `id:` or its file name (e.g. `PM-12` of `PM-12-csv-import.md`), even when it looks like `TASK-001` or `FEAT-001`. The ID of an item inside the document (a task, scenario, contract or question: `BE-1`, `FE-2`, `T-3`, `K1`, `S1`, `C1`, `Q1`) is never the feature's ID; when unsure, note none.
3. Run `read` and find the feature that lists `<file.md>` or `<source.md>`; a new feature (none lists either document) goes under the name step 6 will save. Run "Find the size" for it, under that `name`, with the planned hours of step 2's `doc-stats` (none when it has none).
4. Expected agent time and cost: the agent time, tokens and cost of the references with the chosen SP (their range, naming them); none at that SP → list it as missing.
5. Split suggestion: only on a numeric scale and only at 40 SP or more, suggest how to cut the work into smaller deliverable pieces.
6. Save to the feature step 3 found, reusing its `name`. When it already lists a more detailed document than `<file.md>` (a plan or tasks file for a brief, a tasks file for a plan), show the estimate but save it only after the user confirms; without confirmation save nothing and say the more detailed estimate stays. Run `estimator`, then save, on stdin to `save -`: `{"id", "name", "description", "effort", "storyPoints", "estimatedAt": "<today YYYY-MM-DD>", "estimatedBy": <estimator>, "plan": {"phases", "tasks", "estimatedHours"}, "sources": {"docs": ["<file.md>", "<source.md>"]}}` (no `id` when step 2 noted none; no `<source.md>` without `--from`). Write `description` and `effort` from `<file.md>` (see "Find the size"): `effort` names what makes the work big or small, with no numbers. If `save` reports the SP as frozen, say the original SP stays and the new value is not saved.
7. Report: the SP; the verdicts, e.g. "bigger than A6 (3), same as C4 (5)", and the tie when there is one, or "calculated from N h"; phases, tasks and estimated hours when the file has them; the expected agent time, tokens and cost; the split suggestion; the feature's `file`; and every value that could not be found, `neighbours`', `place`'s and `anchor`'s `missing` lines included.

## `/estimate init`

Builds the references from the delivered features, one per planning-doc set as `find-sets` groups them (a brief, plan, team plan and tasks file of one feature, joined by folder and name, front matter or shared title). A set counts as delivered when `find-sets` gives it `delivered: true` (its plan or tasks file has every task ticked); work without planning docs is skipped.

1. Run `read`, then `find-sets`. Every set with `delivered: true` is one feature: its `docs` and `plan` go to step 2; its `missing` and the top-level `missing` lines go to step 8.
2. **One sub-agent per feature** (inline, one by one, when the harness has no sub-agent tool), given its set's `docs`. Each reads them all together and returns `name`, `description` and `effort` (written from the whole set, see "Find the size"), the feature's `id` (found as in `/estimate` step 2, else null), `docs` (the set's; when it finds a brief, plan, team plan or tasks doc of the same feature that `find-sets` missed, it adds it and says so in its missing values), `taskIds` (every task ID of its plan or tasks file), and its missing values. It runs `check-text` on its `description` and `effort` and rewrites them until `problems` is empty. The feature's `plan` (`{"phases", "tasks", "estimatedHours"}`) comes from `find-sets`, so the sub-agent runs no `doc-stats`. Sub-agents never write the estimate files.
3. **The main agent alone** runs `git-stats` once over all features with `{"features": [{"name", "id", "docs", "taskIds"}]}`: each feature's doc commits and its `candidates`. Shared names and commits can only be told apart with every feature in view.
4. **One sub-agent per feature that has candidates** (inline, one by one, when the harness has no sub-agent tool). It checks each candidate against the feature's name and description, reading the commit (`git show --stat --format=%B <hash>`), and keeps only the commits that do this feature's work (its code, tests or docs). It never keeps a commit because it names the ID: other work that only mentions the ID (e.g. `test(e2e): …` for a feature whose ID is `e2e`) is rejected. It returns the accepted hashes. Sub-agents never write the estimate files.
5. **The main agent alone** runs `git-stats` again and `match-sessions` once, both with every feature's accepted hashes as `commits`. Take their results as they are: never drop, add or re-assign commits or sessions by hand, and never fall back to dates.
6. **The main agent alone** sizes the features by "Find the size"; the judges are sub-agents that see no SP, each given the feature's card from what step 2 returned. Run at most 8 judges at once. Sizes are never decided by lines changed or commits: those are recorded only to check how accurate the estimates were.
   - **The first init** (`read --references` lists none): run `calculate` once with every feature's card, `{"name", "id", "description", "effort", "tasks", "estimatedHours"}` from steps 1–2. A feature with an `sp` is calculated (report "calculated from N h"); place each other feature by "Find the size" with `calculate`'s `pool` as `pool`. When `calculate` gives no `sp` at all (the anchor is off, or no feature has planned hours), ask the user to name an example feature for a few sizes, at least one at 13 SP and one small one; each example keeps the size named, and the examples are the `pool`. This is the one place `init` waits for the user.
   - **Later inits**: every feature that has an `updatedStoryPoints` keeps it; run `calculate` with the cards of the others: those with an `sp` are calculated, the rest placed against the stored references (no `pool`).

   Show one table: name, commits, lines +/−, tasks, hours, sessions, agent time, tokens, cost (from `match-sessions`' `usage`), `matchedBy`, SP (kept, calculated or placed), and `place`'s report or "calculated from N h". Apart from the examples above, never wait for the user: go straight on to step 7 with these values.
7. Run `estimator` once, then `save` each feature: `{"id", "name", "description", "effort", "status": "delivered", "updatedStoryPoints", "updatedBy": <estimator>, "plan": {"phases", "tasks", "estimatedHours"}, "git": {"commits": <git-stats count>, "linesAdded", "linesRemoved"}, "usage": {"matchedBy"}, "sources": {"docs", "commits": <git-stats commits>, "sessions"}}`, with `description` and `effort` from step 2, `git` and `sources.commits` from step 5's `git-stats`, and `matchedBy` and `sessions` from `match-sessions`. `git` and `sources.commits` always go together; send only these fields (an unknown field is rejected). A feature whose stored `usage.matchedBy` is `implement` gets no `usage` and no `sessions`: its recorded sessions are never replaced. `storyPoints` is never sent, so an estimate made before work stays. A kept `updatedStoryPoints` keeps its stored effort; a feature saved before `effort` existed takes the one sent.
8. Report every value that could not be found (from `find-sets`, the sub-agents, `doc-stats`, `git-stats`, `match-sessions`, `calculate`, `neighbours`, `place`, `anchor`), e.g. "P2-03: no session found for 14 of 14 commits".

Running `init` again adds newly delivered features and refreshes the actuals of the others, also of estimated features finished outside `/implement`; it never changes a saved `updatedStoryPoints`.

## `/estimate report`

`report` here is the command word, never a file name. It needs only `$BASE` (no harness, no session-log).

1. Run `report`, with `--out <path>` when the user names one.
2. Report the page's path (it opens offline in any browser; offer to open it), how many features it analyses and how many forecasts it grades, and every `missing` value. With no forecasts, say that the forecast-accuracy section fills once features estimated with `/estimate <file>` before work are delivered. On a "run /estimate init" failure, tell the user to run `/estimate init` first.

Never edit the page by hand: run `report` again after more features are delivered. Whether to commit it is the user's call.

## Record a commit

`/implement` runs this as the last action of the step that commits a task, for the task-breakdown file and the new commit:

```
python3 "$BASE/estimate.py" record-commit <plan-file> <commit> --harness <harness> --session-log "$SESSION_LOG_DIR/session_log.py" --session-dir "$SESSION_DIR"
```

Leave out `--session-log` and `--session-dir` when session-log was not found. It adds the commit's lines, refreshes the plan counts and the feature's slice of the current session (the newest session of `--session-dir`; its prompts, by the `match-sessions` rule over every stored feature's docs and commits, so earlier work of the same session on another feature is not counted), and sets the feature `in-progress`, or `delivered` once every task is ticked. It prints `{"feature", "needsResize", "missing"}`.

- **`needsResize: true`** — the feature was just delivered: re-size it by "Find the size", with its planned hours as delivered (`read`'s `plan.estimatedHours`): calculated from them when it has them and the anchor is on, else placed against the references (no `pool`) — never by lines changed or commits. Then run `estimator` and `save` `{"name": "<feature name>", "updatedStoryPoints": <SP>, "updatedBy": <estimator>, "effort": "<effort>"}`, the effort written from the feature's documents as delivered (see "Find the size"). The original `storyPoints` stays; the same value in both means the estimate was right. Report the verdicts, or "calculated from N h".
- Report the feature's status and every `missing` value. A failure (e.g. "no feature lists <plan>; run /estimate <plan> first") is reported and never blocks the task.
