This skill supports exactly five host identities: `claude`, `codex`, `cursor`, `opencode`, and `omp`.

Select the identity of the host that loaded this skill from runtime/system context. Never infer it from paths, processes, or environment variables. Set `harness` below to that literal identity. Set `BASE` first to the skill directory announced by the host. Set `arguments` to the exact invocation arguments, or to `status` when none were supplied.

```bash
harness='<claude|codex|cursor|opencode|omp: choose the current host>'
BASE='<the skill directory announced by the current host, or empty>'
arguments='<exact invocation arguments, or status>'
case "$harness" in claude|codex|cursor|opencode|omp) ;; *) printf 'session-log: unsupported host identity: %s\n' "$harness" >&2; false ;; esac
if [ ! -f "$BASE/install.sh" ]; then
  BASE=""; for d in "${SESSION_LOG_HOME:-}" .agents/skills/session-log .claude/skills/session-log .cursor/skills/session-log .opencode/skills/session-log .codex/skills/session-log ~/.agents/skills/session-log ~/.claude/skills/session-log ~/.cursor/skills/session-log ~/.config/opencode/skills/session-log ~/.omp/agent/skills/session-log ~/.codex/skills/session-log "$(ls -d ~/.claude/plugins/cache/*/claude-goodies/*/skills/session-log 2>/dev/null | sort -V | tail -1)" "$(ls -d ~/.omp/plugins/cache/plugins/*___omp-goodies___*/skills/session-log 2>/dev/null | sort -V | tail -1)" "$(ls -d ~/.codex/plugins/cache/*/codex-goodies/*/skills/session-log 2>/dev/null | sort -V | tail -1)" "$(ls -dt ~/.cursor/plugins/cache/*/cursor-goodies/*/skills/session-log 2>/dev/null | head -1)" "$(ls -dt ~/.cache/opencode/npm/*/*/node_modules/opencode-goodies/skills/session-log 2>/dev/null | head -1)"; do [ -n "$d" ] && [ -f "$d/install.sh" ] && { BASE="$d"; break; }; done
fi
if [ -n "$BASE" ]; then
  bash "$BASE/install.sh" --harness "$harness" --arguments "$arguments"
else
  printf 'session-log: complete package not found in any known skills root — set SESSION_LOG_HOME=<skill dir>\n' >&2
  false
fi
```

Keep arguments exact and shell-quote the assignment as one data value; never evaluate invocation text as shell syntax. For example, forward `usage --latest` as both words and preserve quoted values. Cursor usage prints Claude Code's per-request layout and price estimate from the parent agent's token counts recorded by Cursor `stop` hooks while logging is on, then lists each subagent with only its final context size from Cursor's local state (not added to TOTAL); it fails rather than inventing totals when none exist. Codex `on` requires the codex-goodies plugin installed from the `user538295` marketplace and adds `~/.codex/hooks.json` commands that run its newest package; until a Codex session has run them, `on` and `status` report `on — approve the session-log hooks in /hooks, or restart Codex and choose 'Trust all and continue' if it shows the 'Hooks need review' screen` (approving in `/hooks` takes effect in the running session; `codex exec` and other non-interactive runs run only hooks already trusted, so trust them once in the interactive TUI). Their text names no package path or version, so plugin updates never change it, and they stay trusted as long as the entries keep their place in `hooks.json`. `status` compares the runtime marker with the running package's `VERSION`, so run it through the plugin's skill; a checkout with another `VERSION` keeps reporting the instruction. Without the plugin, Codex `status` reports `on — codex-goodies plugin not installed`.

In Claude Code the claude-goodies plugin's `hooks/hooks.json` always registers the session-log hooks, which stay idle until `on` creates the enable flag (when Cursor imports the enabled plugin and runs them, only the session-start hook runs the legacy cleanup, and none of them logs, nor writes or removes Claude runtime markers); `on` and `off` only flip that flag, and `status` only reads it together with the runtime marker the hooks of a running session write. Cursor works the same way through the cursor-goodies plugin's `.cursor-plugin/hooks.json`, which Cursor loads only while its "Include Third-Party Plugins, Skills, and Other Configs" setting is on (and its server-side plugin import gate allows it); the hooks run with no prompt, through the user's `$SHELL -c`, and each command checks the enable flag first, so while logging is off the plugin's hooks exit immediately without starting Python (legacy `~/.cursor/hooks.json` entries still run the older code until the cleanup removes them), and they exit silently when the plugin's hook script is missing. The commands are tested with sh, bash, zsh, and fish; shells with another syntax (for example nushell, xonsh, or PowerShell) fail on every event, which Cursor records only in Cursor Settings → Hooks (no notification); native Windows is not supported for these hooks (Cursor runs them through PowerShell there), so use Cursor under WSL. Cursor's first `on` reports `on — logging starts with the next prompt once the cursor-goodies hooks run; run status after it to confirm`. When logging is on but no hook of this cursor-goodies version has run, `status` reports `on — no hook of this cursor-goodies version has run` and names the plugin install or update, that setting, and a restart; it counts only hooks of the same package `VERSION` as this skill, and failing hook runs are listed in Cursor Settings → Hooks. In OMP the omp-goodies plugin registers the session-log extension, which logs nothing until `on` creates the enable flag and reads that flag at every prompt; it still writes its runtime marker and starts the legacy cleanup when it loads, so `on` reports `on — restart required` until a restarted omp has loaded it. A failed background cleanup is reported on omp's stderr; `repair` names the cause.

`repair` removes duplicate and stale session-log hook registrations and the leftovers of older releases for the current host, and reports what it changed: Codex `hooks.json` entries (restoring the missing ones of a partial set, and in Codex, while the codex-goodies plugin is installed, replacing the entries older releases registered by package path), the package copy older releases seeded into `~/.codex/skills` (removed only when proven unchanged, as in Claude Code below, and kept while `~/.codex/hooks.json` names its hook or cannot be read, because Codex sessions started earlier keep running that hook; restart Codex before the next `on` or `repair`, which then removes it, since neither can tell whether Codex restarted; without the plugin `repair` keeps it and says to install the plugin, then run `on`), every session-log entry older releases put in Cursor's `~/.cursor/hooks.json` plus the package copy they seeded into `~/.cursor/skills` (only when its ownership manifest proves every file unchanged; otherwise `repair` names it, and since a kept, changed copy re-registers its `~/.cursor/hooks.json` entries whenever it is used, move it aside) and their adapter state files (each Cursor session start while logging is on runs `repair` when `~/.cursor/hooks.json` still holds such entries), dangling OpenCode adapter links that point into the claude-goodies plugin cache, in OMP the `~/.omp/agent/extensions/session-log.js` link, the package copy older releases seeded into `~/.omp/agent/skills/session-log` and its usage link, and in Claude Code every session-log hook in `settings.json`, the legacy prompt_log scripts the pre-plugin install copied into `~/.claude/scripts` and their hooks, plus the package copy (or a skill-root link into the plugin cache) older releases left under `~/.claude/skills` (a copy only when its ownership manifest proves every file unchanged; otherwise `repair` names it so you can move it aside). An edited legacy script keeps the scripts and their hooks, and `repair` then fails naming it. OpenCode and OMP adapter copies and `session-log-omp` files of pre-universal releases go silently; in Codex and OpenCode `status` and `usage` run the same cleanup when they repair an enabled adapter. `on` runs the cleanup first; in Claude Code, Cursor, and OMP it still turns logging on when the cleanup fails (naming the failure) or is skipped because another session-log command is running. Each Claude Code startup runs it silently, once per change of `settings.json`, the session-log package (its location or `VERSION`), or the presence of that seeded copy or those scripts, whether or not the attempt succeeds. Each omp start runs it in the background while those leftovers remain. On native Windows only the Claude Code plugin's hooks run (under Git Bash); `on`, `off`, `repair`, and the startup cleanup need WSL; there the startup attempt fails silently once per such change.
